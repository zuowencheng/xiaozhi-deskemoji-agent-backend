# 重复派单拦截 + 顺带修出的两个严重缺陷（2026-10-03 21:20）

## 起因

30 条任务失败 7 条，6 条都是"助理步数用尽"。复盘发现根因不是助理不行，
而是**派了不该派的单**——同一个活反复派：

| 时间 | 派的任务 | 真实情况 |
|---|---|---|
| 04:56 | 开通火山语音合成 | TTS 早已切 uranus |
| 05:04 | 开通火山语音合成（又来一次） | 同上 |
| 12:26 | 关掉开场提示音 | 固件/配置早已处理完 |

这些事**记忆里有结果，但派单时没查**。

## 一、重复派单拦截（双层）

### 提示词层（`agent-base-prompt.txt`）

`<pc_control_rule>` 加【派单前三道闸】：

1. **先 `recall` 查记忆** —— 干过的事直接答"早就弄好了"；本机配置层面的事
   （换音色、调音量、清临时文件）根本不用派
2. **手机上的事不派** —— 本机助理够不到手机（"用 workbody 开美团"）
3. **硬件故障不派** —— 显示器没信号、线松了，要人上手

外加【派单要干净】：一次只派一件事，多目标任务**整单失败**（助理有步数上限）。

`pc_run_task` 的 tool description 也同步写了这三道闸——
描述在每次工具调用时都会进上下文，比只写系统提示词更稳。

### 代码层（机械兜底，不依赖模型自觉）

`pc_control.py` 新增 `pc_run_task` 派单前的重复检查：

- `_keywords()`：清洗后抽 2/3/4 字片段（中文关键词多为双字，
  再加 3~4 字"要点词"拉开差异）+ 停用词表
- `_recent_history()`：扫最近 60 条任务单（**done + failed 都算**）
- 重合度 ≥ `_DUP_RATIO`(0.8) → 直接挡回，返回指令让小智改口告诉主人

## ⚠️ 三个实测踩出来的坑

### 坑 1：状态字面量是 `done` 不是 `completed`

第一版写 `if d["status"] == "completed"` → **一条都匹配不上，兜底静默失效还不报错**。
实测 `bridge/done/` 41 个文件：34 个 `done`、7 个 `failed`。

→ 已抽成常量 `_STATUS_DONE` / `_STATUS_FAILED` 并注明。

### 坑 2：⚠️ `failed` 的任务单也必须纳入比对

上面那三条"我们早就做完的事"在 done 里状态**全是 `failed`**（助理没做成）。
只查 `done` 的话 4 个重复活只拦下 1 个。

而且 failed 恰恰**最该拦**：它说明"这事派过了、没做成"，再派大概率同样结果。
而"真没做过的事"本来就不在 done 里，天然不会误拦。

→ 改成 `_recent_history()` 收 done + failed。

### 坑 3：正则往 YAML 里插行会把配置写坏

`_ensure_llm_section()` 第一版用正则找 `LLM:` 段末尾插入，
结果 `DoubaoLLM:` 那一行**带尾冒号无子键**，插在它下面拼成
`DoubaoLLM:  QwenLLM:` → YAML 直接崩。

**幸好先在副本上测**，且代码里有 YAML 自检 + 自动回滚，真配置没被破坏。

→ 改成 `yaml.safe_dump` 整体重写 + 写后自检 + 失败回滚。
（代价是注释丢失，但这是 `data/` 下私有配置，可接受。）

## 二、★★ 顺带挖出：切模型会把后台搞坏（`llm_switch.py`）

**这才是今天最大的雷**。

### 现象

19:17:58 你让小智切通义千问，它回报"已切换（立即生效=True）"。
**19:19 重启后台后直接起不来**：
```
KeyError: 'QwenLLM' @ core/utils/modules_initialize.py:41
```
只能手工把 `selected_module.LLM` 改回 `DeepSeekLLM` 才救回来。

### 根因（读写不对称）

`llm_profiles` 里档案分两种写法：

| 类型 | 特征 | 切过去会怎样 |
|---|---|---|
| **引用式** | 只有 label/note，真配置在 `LLM:` 段同名下（如 `DeepSeekLLM`） | 重启 OK |
| **完整式** | 自带 type/model_name/base_url/api_key（如 `QwenLLM`） | **重启 KeyError** |

`switch_llm` 只改了 `selected_module.LLM` 一个字段，
而 `modules_initialize.py:41` 只认 `config["LLM"][name]`。
→ **能切、不能重启**，切换功能等于把后台搞坏。

### 修法

新增 `_ensure_llm_section(name)`：切换成功后若 `LLM:` 段没有同名条目，
把档案的**运行时字段**（`type/model_name/base_url/api_key/temperature/max_tokens/timeout`）
补写进去。写完做 YAML 自检，失败自动回滚 `selected_module`。

实测（在副本上）：
```
切到 QwenLLM        → (True, '已补写 LLM.QwenLLM')
LLM 段键            → [..., 'QwenLLM']
模拟启动取 type     → QwenLLM: type=openai  OK 可实例化
重复切              → (True, 'LLM 段已有同名配置')   幂等
引用式 DeepSeekLLM  → (True, 'LLM 段已有同名配置')
不存在的档案        → (False, 'llm_profiles 里没有 NotExistLLM')
```

## 教训

1. **写兜底逻辑必须用真实数据验证**，不能写完就上线。
   第一版"历史已完成任务数: 0"就是静默失效的信号——
   幸好我多跑了一步验证，否则这层防护等于没有。
2. **"能切换成功"不等于"切换后系统还能用"**。
   任何"改配置并持久化"的功能，都必须问一句：
   **改完之后重启，这个配置还成立吗？**
3. **改配置类功能优先在副本上试**，并带自动回滚。
   这次正是副本测试 + 自检回滚，挡住了会写坏真配置的一版实现。
