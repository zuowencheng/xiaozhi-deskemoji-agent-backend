# 21 · 设备卡死故障诊断与修复（Task WDT / LVGL 显示冻结）

> 日期：2026-10-02
> 现象：唤醒后说了一句话，设备卡住，屏幕停在"说话中"，不再响应
> 结论：**已定位并修复**（LVGL 显示刷新死等导致的 CPU 饿死 + 看门狗触发）

---

## 一、现象与第一现场

用户反馈：能唤醒、能对话一两句，随后**卡住不动**，屏幕显示"说话中"。

### 1.1 后台侧：一切正常

`_server_run.log` 显示这轮对话**服务端已经完整走完**：

```
17:52:24  设备上线: 84:c7:bb:58:17:44（当前在线 1）
17:52:24  收到listen消息: 文本"你好小智"
17:52:24  播放唤醒词回复: 来啦来啦，请告诉我吧。
17:52:30  识别文本: 目前。
17:52:33  发送第一段语音: 目前？
17:52:35  发送音频消息: ...你这半句话是想让我接什么啦，笑死
17:52:37  发送音频消息: SentenceType.LAST, None      ← 服务端判定本轮结束
```

**关键判断：卡点不在服务端，也不在语音链路**（ASR/LLM/TTS/WS 全部正常）。

### 1.2 设备侧：抓到"铁证"

读串口（COM3），设备只吐了 526 字节，全是这一句：

```
E (4377117) task_wdt: Task watchdog got triggered.
           The following tasks/users did not reset the watchdog in time:
E (4377117) task_wdt:  - IDLE1 (CPU 1)          ← IDLE 任务被饿死
E (4377117) task_wdt: Tasks currently running:
E (4377117) task_wdt: CPU 0: main_event_loop
E (4377117) task_wdt: CPU 1: taskLVGL           ← LVGL 任务占满 CPU1
E (4377117) task_wdt: Print CPU 1 backtrace

Backtrace: 0x4037BDC3 0x4037B24D 0x420B7DD1 0x420B8767
           0x420B8895 0x420B9095 0x420C2576 0x420B0814
```

**看门狗语义**：IDLE 任务优先级最低（0）。如果某个更高优先级任务**一直不让出 CPU**，IDLE 得不到调度就会触发 WDT。这里被饿死的是 **CPU1 上的 IDLE1**，而 CPU1 上正在跑的是 **taskLVGL**。

## 三、根因（三个缺陷叠加）

### 3.1 缺陷一：LVGL 的等待是"裸忙等"

LVGL 9.3 源码 `lv_refr.c:1415`：

```c
static void wait_for_flushing(lv_display_t * disp)
{
    lv_display_send_event(disp, LV_EVENT_FLUSH_WAIT_START, NULL);

    if(disp->flush_wait_cb) {
        if(disp->flushing) {
            disp->flush_wait_cb(disp);
            disp->flushing = 0;
        }
    }
    else {
        while(disp->flushing);      // ★ 没有 delay、不让出 CPU
    }
    ...
}
```

**`flush_wait_cb == NULL` 时走 `while(disp->flushing);`** —— 纯自旋，**不调用任何阻塞/让出函数**。只要 `flushing` 不清零，这里就是**死循环**。

### 3.2 缺陷二：I2C 屏的 flush_ready 只能靠"传输完成回调"

板子的屏幕是 **I2C 的 SSD1306（128×64）**，不是 RGB/DSI 屏。

`esp_lvgl_port` 的 `lvgl_port_flush_callback` 结尾：

```c
} else {
    esp_lcd_panel_draw_bitmap(disp_ctx->panel_handle, ..., color_map);   // 异步提交，未检查返回值
}

if (disp_ctx->disp_type == LVGL_PORT_DISP_TYPE_RGB ||
   (disp_ctx->disp_type == LVGL_PORT_DISP_TYPE_DSI && ...)) {
    lv_disp_flush_ready(drv);      // ★ 只有 RGB/DSI 才在这里调
}
```

对 I2C 屏，`flush_ready` 的唯一触发点是这个回调（IDF ≥ 4.4.4，宏为 1）：

```c
#if LVGL_PORT_HANDLE_FLUSH_READY          // IDF 5.5.4 → 1
    const esp_lcd_panel_io_callbacks_t cbs = {
        .on_color_trans_done = lvgl_port_flush_io_ready_callback,   // ← 唯一清 flushing 的地方
    };
    esp_lcd_panel_io_register_event_callbacks(disp_ctx->io_handle, &cbs, disp);
#endif
```

**一旦 `on_color_trans_done` 没被触发（I2C 忙 / 超时 / 事务被拒），`flushing` 永远停在 1**，而 `lvgl_port_flush_callback` 又**没有检查 `draw_bitmap` 的返回值**，不会被发现。

### 3.3 缺陷三：同一条 I2C 总线上还挂着一个高优先级"搅局者"

板级 `board_config.h`：

```c
#define DISPLAY_I2C_SDA_PIN GPIO_NUM_41
#define DISPLAY_I2C_SCL_PIN GPIO_NUM_42
#define DISPLAY_I2C_ADDR    0x3C

#define GESTURE_I2C_SDA_PIN GPIO_NUM_41     // ← 手势传感器与屏幕共用同一条 I2C
#define GESTURE_I2C_SCL_PIN GPIO_NUM_42
#define GESTURE_I2C_ADDR    0x73
```

而手势任务的**优先级比 LVGL 高得多**（`gesture_sensor.cc`）：

```cpp
xTaskCreate(GestureTaskFunction, "GestureTask", 8192, this,
            7,        // ← 优先级 7
            &gesture_task_handle_);

while (sensor->task_running_) {
    GestureType gesture = sensor->ReadGesture();   // 每 50ms 敲一次 I2C
    ...
    vTaskDelay(pdMS_TO_TICKS(50));
}
```

对比 `oled_display.cc` 里 LVGL 的配置：

```cpp
port_cfg.task_priority = 1;      // ← LVGL 只有 1
port_cfg.task_stack    = 6144;   // 6KB
port_cfg.task_affinity = 1;      // 绑定 CPU1
```

> 注意：手势任务确实有一把自己的 `i2c_mutex_`（"I2C互斥锁已设置，启用总线共享协调"），
> 但**屏幕驱动走的是 esp_lcd_panel_io，根本不经过这把锁** —— 所以两边对总线的竞争依然存在。

I2C 速率已是 400kHz，传一屏 1024 字节约 23ms。手势任务每 50ms 抢一次总线（一次约 1ms），
**屏幕上一次传输还没完成、下一次 flush 就来了 → `bus_busy` → `draw_bitmap` 失败 → 完成回调丢失**。

> 补充：手势传感器本身是**正常的**（启动日志显示软复位成功、219/219 寄存器写入成功），
> 健康检查里的 `总成功: 0` 只是"没检测到手势动作"，不是故障。

### 3.4 完整因果链

```
手势任务(prio 7) 与屏幕共用 I2C(400k)
        │  每 50ms 抢总线
        ▼
屏幕 draw_bitmap 偶发失败（bus_busy / 超时）
        ▼
esp_lcd 不触发 on_color_trans_done 回调
        ▼
lv_disp_flush_ready() 未被调用 → disp->flushing 停在 1
        ▼
LVGL 9.3 wait_for_flushing() 执行 while(disp->flushing);
        │  （无 flush_wait_cb，裸自旋）
        ▼
taskLVGL（prio 1，CPU1）占满 CPU1，永不让出
        ▼
CPU1 上的 IDLE1（prio 0）彻底饿死
        ▼
Task WDT 触发 → 串口刷 backtrace → 整个 UI 冻结
（但语音链路仍在后台正常收发，所以后台日志看起来"一切正常"）
```

## 四、修复

### 4.1 改动内容

**文件**：`firmware/community/main/display/oled_display.cc`
**改动**：给 LVGL 显示注册 `flush_wait_cb`（2 处小改）

```cpp
#include <freertos/FreeRTOS.h>
#include <freertos/task.h>
...
    display_ = lvgl_port_add_disp(&display_cfg);
    if (display_ == nullptr) { ESP_LOGE(TAG, "Failed to add display"); return; }

    /* 【冻结修复 2026-10-02】
     * 注册 flush_wait_cb 后，LVGL 的 wait_for_flushing() 改走另一分支：
     * 等待期间主动让出 CPU，并在回调返回后强制清零 flushing 计数。
     * 这样即使 I2C 完成回调丢失也不会死锁，最坏只丢一帧画面。
     */
    lv_display_set_flush_wait_cb(display_, [](lv_display_t *disp) {
        vTaskDelay(pdMS_TO_TICKS(1));
    });
```

**为什么有效**：

| 路径 | `flush_wait_cb == NULL`（修复前） | 注册后（修复后） |
|---|---|---|
| 正常（回调来了） | `flushing` 已清零，**不进分支**（零开销） | 同左（零开销） |
| 异常（回调丢了） | `while(flushing);` **死循环 → 系统冻结** | 调回调让出 1ms，**强制清零**，继续跑 |

* 正常路径**零性能开销**（回调到达时 `disp->flushing` 已是 0，根本不进 if 分支）
* 异常路径**优雅降级**：最坏丢一帧画面，绝不冻结系统

### 4.2 编译与刷机

```bash
# 增量编译（复用 tools/_rebuild_quick.py，内含 MSYSTEM 清理）
python tools/_rebuild_quick.py
#   产物 firmware/community/build/xiaozhi.bin = 2,759,680 字节（4MB 分区余 34%）

# 写进 ota_1（0x500000），不碰 ota_0
esptool --chip esp32s3 --port COM3 --baud 460800 write_flash 0x500000 build/xiaozhi.bin
#   Wrote 2759680 bytes ... Hash of data verified.
```

### 4.3 验证（重要）

**⚠️ 踩坑记录：增量编译不会更新 `app_desc` 的 `Compile time`。**

刷完机读串口，`app_init: Compile time` 仍显示上一版的 `Oct 2 2026 15:40:52`，
一度让人以为"写入没生效"。**实际上固件已经更新了。**

**判断固件身份的正确方法 —— 比对 ELF SHA256**（串口启动日志会打印）：

```
串口日志 : app_init: ELF file SHA256: ea0a6f1fe...
本地计算 : sha256(build/xiaozhi.elf) = ea0a6f1fe955ab441d89a10d0569715ebf4e96129e3d3b20e49ec07df0b02d9f
           ↑ 前 9 位完全一致 → 设备确实在跑新编的固件
```

**结论：以后一律用 ELF SHA256 判断固件，不要用 Compile time / 版本号。**

### 5.2 长期验证方法

此故障是**概率性**的（运行约 1 小时后才撞上）。修复后需要**长时间运行观察**：

```bash
# 观察是否还会出现 watchdog
grep -c "task_wdt" firmware/device_dump/serial_*.log
```

### 5.3 遗留问题（不影响语音，待后续处理）

**① 表情图层创建失败** —— 串口持续出现：

```
W EmojiController: ExecuteRandomAnimation: 屏幕或眼睛对象不存在     （本次抓包出现 7 次）
```

`emoji_screen_ / left_eye_ / right_eye_` 为 `nullptr`，导致**所有表情动画被跳过**（桌宠的屏幕表情不动）。
根因待查（可能是表情屏幕创建时机/分辨率与 128×64 OLED 不匹配）。

**② 根治 I2C 竞争（本次只是止血）** —— 当前修复保证"不冻结"，但没有消除竞争本身。可选后续方案：

- 让屏幕的 I2C 访问与手势任务共用同一把互斥锁
- 或降低手势任务优先级（7 → 3 左右）/ 拉长轮询间隔
- 或在 `text` 层给手势功能加开关

**③ `SuspendLVGLTask()` 是空实现** —— `emoji_controller.cc:3518`：

```cpp
// 暂停LVGL任务（空实现，防止链接错误）
void EmojiController::SuspendLVGLTask() {
    // TODO: 实现暂停LVGL任务的逻辑
}
```

而 `ResumeLVGLTask()` 却在做真事（查找 taskLVGL 并恢复优先级）。
两个函数**不对称**，虽然因 `lvgl_task_suspended_` 恒为 false 而未产生实际危害，但属于明显的代码缺陷，建议后续清理。

## 六、回滚保命

如需退回原厂固件（ota_0）：

```
双击 tools/rollback_to_ota0.cmd
```

原理：擦掉 otadata 的 slot1 扇区（0xE000）→ bootloader 找不到 seq=2 的记录，
自动回退到 slot0（seq=1 → ota_0）。

备份齐全：`hardware/reports/backup_20261002_16MB.bin`（整片）、
`hardware/reports/rollback_kit/ota_0_app.bin`（ota_0 单独 4MB）。
