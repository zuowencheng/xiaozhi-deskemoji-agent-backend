# 59 · 免打扰时段 + 聆听超时

> 2026-10-04 凌晨。主人提两个需求：
> ① 后台加"几点之后不再主动通知"的设置（默认关、默认 23 点起）；
> ② 小智说完话一直挂在"聆听中"，想让这个状态默认 180 秒（或 120 秒）后结束。
>
> 结论：**①纯服务端就能做；②服务端够不着，必须改固件**。两个都做完了。

---

## 一、需求 ① 免打扰时段（服务端，已做）

### 设计要点

| 决定 | 选择 | 理由 |
|---|---|---|
| 拦截点 | `speak_or_queue()` + `_drain_queue()` **两处** | 只拦一处会漏：设备在线时，`_drain_queue` 每 5 秒补播一次，会把队列立刻播掉，静默形同虚设 |
| 静默期消息 | **入队，不丢弃** | 半夜念一句你也听不见；留到白天补播才有意义 |
| 影响范围 | **只拦主动播报** | 你问它答的对话**不走** `speak_or_queue`，所以深夜照常聊天，只是它不主动开口 |
| 起止相同 | 视作**无效配置**，返回"不静默" | 手滑填成 23:00/23:00 若按"全天静默"处理，会变成"我什么都收不到但日志一切正常"——最难查的一类故障 |

### 配置（`data/.config.yaml` 新增 `notify` 段）

```yaml
notify:
  quiet_hours_enabled: false     # 默认关闭
  quiet_hours_start: "23:00"     # 起点（含）
  quiet_hours_end: "07:00"       # 终点（不含）。起点 > 终点 = 跨过零点
```

⚠️ **时间必须带引号**。YAML 1.1 会把裸写的 `23:00` 当**六十进制**解析成整数 `1380`、
`07:00` 解析成 `420`。管理台保存时会自动加引号；`_hhmm_to_min()` 也兼容整数，双重保险。

### 跨午夜判据（容易写错的那行）

```python
if s < e:   return s <= cur < e          # 不跨零点，如 01:00→06:00
else:       return cur >= s or cur < e   # 跨零点，如 23:00→07:00
```

写成 `s <= cur <= e` 的话，23:00→07:00 这个默认配置会**永远返回 False**（静默永不生效），
而且不报错——典型的静默失效。

### 改动文件

| 文件 | 改动 |
|---|---|
| `core/notify_plugin.py` | 新增 `_notify_cfg()` / `_hhmm_to_min()` / `_in_quiet_hours()`；`speak_or_queue` 静默期入队；`_drain_queue` 静默期休眠 |
| `server/admin/admin_server.py` | EDITABLE 加 3 项（新增 `time` 类型，落盘自动加引号）；新增"免打扰"分组 |
| `data/.config.yaml` | 新增 `notify` 段 |

## 二、需求 ② 聆听超时（固件，已做）

### 根因：为什么它会一直"聆听中"

固件 `application.cc` 里，TTS 播完（`tts/stop`）之后的走向是：

```cpp
if (device_state_ == kDeviceStateSpeaking) {
    if (listening_mode_ == kListeningModeManualStop) {
        SetDeviceState(kDeviceStateIdle);       // 手动模式 → 待机
    } else {
        SetDeviceState(kDeviceStateListening);  // 自动模式 → 继续聆听
    }
}
```

`git diff` 确认过：**这段是上游原版，不是本地改的**。而语音唤醒走的是 `AutoStop` 模式
（`application.cc:284`：`aec_mode_ == kAecOff ? kListeningModeAutoStop : ...`，本板无 AEC），
所以**每轮对话结束必然回到 listening**。

那官方设备为什么不会卡住？因为上游还有第二道：服务端无语音 `close_connection_no_voice_time`
秒后关闭连接，设备随之回待机。而**我们为了"主动播报随时能推"把这个值改成了 86400（常连）**，
第二道闸被拆了 → 设备永远停在聆听中。

### 为什么这个不能只改服务端

试过两条路，都不通：

1. **改 `close_connection_no_voice_time` 回 180** —— 无效。
   这个超时在 `receiveAudioHandle.py::no_voice_close_connect()` 里检查，
   而它**只在收到音频帧时才被调用**。设备在 listening 但你不说话时，
   AFE 的 VAD 没检测到语音就**不发音频帧**（`application.cc` 只有 VAD 命中才入发送队列），
   服务端永远等不到帧，超时永不触发。
2. **让服务端发 `listen stop` 命令** —— 无效。
   固件 `OnIncomingJson` **根本不处理 `listen` 这个 type**（`protocols/*.cc` 里也没有）。
   按铁律 4b，不能自造协议。

→ **只能改固件**：在每秒的 `CLOCK_TICK` 里自己计时。

### 180 还是 120？（主人问哪个更科学）

说实话：**没有实测数据支撑"哪个更优"**，所以我把它做成了可调，并用下面这个更稳的判据：

- 计时是**"连续听不到声音"的秒数**，`IsVoiceDetected()` 为真就清零 ——
  所以 180 秒不是"对话开始后 180 秒"，而是"**沉默** 180 秒"。真人对话中沉默 3 分钟，基本就是结束了。
- 误触成本：listening 时麦克风一直开，环境噪声（电视、键盘、旁人说话）可能触发 VAD → ASR → LLM，
  每次都是真金白银。但这类误触发本身不多，180 与 120 之间差 60 秒，省下的钱**很有限**。
- 体验成本：超时回待机后想继续聊**要重新说唤醒词**。这是唯一的代价，也是 120 相对 180 的主要风险。

**建议先用 180 观察几天**（更不容易打断"我想一下再问"）。嫌久就在后台调 120/60，
**改完重启后台即可，不用刷机**（握手时下发）。

### 实现

| 位置 | 改动 |
|---|---|
| `protocols/protocol.h` | 新增 `listening_timeout_sec()` getter + 成员（默认 180，0/负数 = 永不超时，退回上游行为） |
| `protocols/websocket_protocol.cc` | `ParseServerHello()` 读 `listening_timeout_sec` |
| `main/application.h` | 新增 `listening_silent_ticks_` |
| `main/application.cc` | `CLOCK_TICK` 里每秒检查：有声音清零，连续 N 秒无声 → `SetDeviceState(kDeviceStateIdle)`；进入 listening 时清零 |
| `core/connection.py` | `welcome_msg` 加 `listening_timeout_sec`（握手下发） |
| `.config.yaml` / 管理台 | 顶层 `listening_timeout_sec: 180`，管理台"交互"组可调 |

## 三、与现有时间设置的冲突检查（主人问的重点）

| 现有设置 | 当前值 | 是否冲突 | 说明 |
|---|---|---|---|
| `close_connection_no_voice_time` | 86400（常连） | **不冲突** | 聆听超时只改**设备状态**（listening→idle），**不断开 WebSocket**。主动播报链路完好 |
| `min_silence_duration_ms`（VAD） | 700 | 不冲突 | 一个管"一句话说完没"，一个管"整轮对话还要不要继续听" |
| `threshold_low` | 0.3 | 不冲突 | 同上 |
| `tts_timeout` / `tool_call_timeout` | 15 / 30 | 不冲突 | 只作用于单次调用 |
| `greeting_debounce` | 600 | 不冲突 | 唤醒问候去重，独立逻辑 |
| 免打扰 vs 唤醒对话 | — | 不冲突 | 对话不走 `speak_or_queue`，深夜照样能聊 |
| 免打扰 vs 任务回执 | — | 会被拦 | 静默期的"好的，正在处理"也一起静默（合理，否则照样吵） |
| 免打扰 vs 定时提醒 | — | **入队延后** | 静默期内到点的提醒不会丢，出静默窗口后补播 |

⚠️ 一个待观察点：静默一整夜后，早上可能**一次补播好几条**。目前不做合并（先观察实际数量），
如果觉得吵，下一步可以把同 tag 的合并成一句"昨夜有 3 件事：…"。

## 五、行为变化（要提前知道的）

1. **回待机后要重新唤醒**（说"你好小智"）才能继续对话 —— 这是 180 秒超时的唯一代价。
2. 回待机**不断开连接**，主动播报、定时提醒不受任何影响。
3. 免打扰默认**关闭**，需要你自己去后台打开（默认 23:00 → 次日 07:00）。
4. 静默期的消息不丢，会在早上补播。
