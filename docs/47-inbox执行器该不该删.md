# inbox 任务执行器：该不该删？（2026-10-03 实测结论：不能删，但修了个 bug）

> 主人疑问：「这个定时任务跑了好长时间，其实是不是一条也没捞到正常数据？还需要吗？
> 不需要的话直接删除是不是可以」

---

## 一、先看实际数据：它一直在干活，而且成功率不低

`bridge/done/` 里的任务统计（**22 个真实任务**）：

| 状态 | 数量 | 占比 |
|---|---|---|
| ✅ `done` | **19** | **86%** |
| ❌ `failed` | 3 | 14% |
| 合计 | 22 | |

**3 个失败的原因完全一致**：

```
这活儿步骤太多，我没能在限定步数内干完，建议拆成小任务再说一遍。
```

也就是说：**失败不是循环的问题，是任务本身太复杂**（比如"打开QQ"这种要装填路径、
找可执行文件、还要处理窗口聚焦）。拆成"打开开始菜单"+"输入QQ"就能成。

**结论：不能删。** 它是"小智派活给电脑"这条链路的执行端，删了整个功能就没了。

---

## 二、它到底是干什么的

```
你对小智说"在电脑上打开网易云音乐"
        ↓
LLM 调 pc_control → 写一个 task-*.md 到 bridge/inbox/
        ↓
_notify_plugin._execute_inbox_loop  ← 就是这个循环，每 3 秒扫一次 inbox
        ↓
调 core/pc_agent.execute_task_file → 把任务派给本机 WorkBuddy 执行
        ↓
结果写回 bridge/done/（状态改成 done/failed）
        ↓
取件 watcher 发现新文件 → 小智主动开口播报"干完了"
```

三个文件目录分工：
| 目录 | 作用 |
|---|---|
| `bridge/inbox/` | 待处理的活儿（小智写进来） |
| `bridge/done/` | 处理完的活儿（写结果、标状态） |
| `bridge/announced/` | 已播报过的标记（防重复念） |

**没有这个循环，`inbox` 就是一个没人管的空目录。**

---

## 三、但你的直觉对了一半：确实有任务卡住了

我查的时候发现 `inbox/` 里躺着一个任务，状态 `running`，**将近一小时没动**：

```
inbox/task-20261003-045507.md   ← "在电脑上打开腾讯的QQ应用程序"  状态：running
```

而 `done/` 目录里 **0 个 running**（它压根没被移过去）。这是不对的。

### 根因（这是个真 bug）

`core/notify_plugin.py` 的执行器主循环：

```python
for f in sorted(inbox.glob("task-*.md")):
    if f.name in _EXEC_RUNNING:
        continue
    ...
    if "- 状态：pending" not in head:
        continue          # ★ running/done/failed 都不碰
    _EXEC_RUNNING.add(f.name)
    asyncio.create_task(_run_one_task(f))
```

任务被取走时状态改成 `running`，如果这两种情况发生：

1. **执行器抛异常**（比如 WorkBuddy 那边超时/崩溃）
2. **服务重启**（改配置、切 TTS、端口冲突……）

任务就永远停在 `running`。而主循环**只认 `pending`**，
`"- 状态：pending" not in head` 永远成立 → **这个任务被永久跳过**。

`_EXEC_RUNNING` 那个内存集合在 `finally` 里清理，但**服务重启后内存清空、文件状态还是 running**，
两者对不上，任务就成了僵尸。

**今晚服务重启了 27 次**（改配置、切火山 TTS、调 VAD…），所以撞上了这个坑。

---

## 四、修复：僵尸任务自动回收

新增 `notify_plugin._reap_stale_tasks()`，每轮扫描时先清一遍：

| 参数 | 值 | 说明 |
|---|---|---|
| `_STALE_RUNNING_SEC` | **900 秒（15 分钟）** | running 超过 15 分钟且不在执行中 → 判为僵尸 |
| 处理方式 | 标记 `failed` + 写明原因 + 移到 `done/` | 留痕迹，不静默吞掉 |
| 附加动作 | 小智主动播报「有个任务卡住了，我判定它失败了」 | 你能第一时间知道 |
| 防重复 | `_reaped` 集合 | 同一轮不会重复处理同一个文件 |

### 验证结果

```
05:53:52  回收僵尸任务 task-20261003-045507.md（running 超过 57 分钟）
```

回收后：
- `inbox/` 任务数：**0** ✅
- `done/` 状态分布：**19 done / 4 failed**（那个僵尸任务已归入 failed）

## 五、如果你还是想省资源

这个循环**每 3 秒**扫一次目录，开销就是"读几个小文件"，几乎不耗 CPU。真要调整：

```yaml
notify:
  exec_poll_interval: 3      # → 改成 10 也无妨（响应慢 7 秒而已）
  exec_enabled: true         # → 改成 false 可整体关停
```

配置在 `data/.config.yaml` 的 `notify:` 段。

**但我建议别关**——它是"小智真正动手干活"的执行端，
关掉之后小智只能动动文件、发发消息，没法真的操作你电脑。

---

## 六、真正该改的是这两个

1. **复杂任务拆细**：失败的那 3 个都是"步骤太多"。
   以后可以对小智说"打开网易云音乐"而不是"打开网易云音乐并搜索周杰伦的歌单"——
   一步一件事，成功率会明显上去。

2. **考虑加超时兜底**：如果 WorkBuddy 那边卡得更久（超过 15 分钟），
   现在会被判 failed；这个阈值可以在配置里调。
