# "无法连接服务"提示擦不掉 —— 上游自带缺陷（2026-10-03 19:20，已修并刷机）

## 现象

后台重启后，屏幕一直显示 Alert 弹出的：

```
无法连接服务，请稍后再试
(circle_xmark 图标)
```

**关键矛盾**：服务端日志明明写着设备已上线（`设备上线: 84:c7:bb:58:17:44`），
WS 通道是通的，但**屏幕就是不对**。

**迷惑性**：不唤醒小智永远擦不掉，一唤醒立刻恢复正常。

---

## 根因（已对照上游 HEAD 确认，非本地改坏）

调用链断在最后一环：

```
websocket_protocol.cc   ✗ 从不调用 on_connected_()
        ↓
application.cc:425     protocol_->OnConnected([]{ DismissAlert(); })
        ↓
application.cc:247     DismissAlert() ← 清错误提示、恢复 STANDBY
        ↓
屏幕永远停在错误文案
```

- `Application::DismissAlert()`（清提示 + 恢复 STANDBY）**只在**
  `protocol_->OnConnected(...)` 回调里被调用（`application.cc:425`）
- 而 `Protocol::OnConnected` 注册的 `on_connected_`：
  - **MQTT 会调用**：`mqtt_protocol.cc:86-88`
  - **WebSocket 从不调用**：`git show HEAD:main/protocols/websocket_protocol.cc`
    全文搜不到 `on_connected_`

→ **走 WS 的设备永远收不到"已连接"通知**，错误提示永久驻留。
唤醒后之所以恢复，是因为唤醒流程 `StartListening` 里另有 `OpenAudioChannel()`
触发路径会重新走一遍状态更新（属于"歪打正着"，不是设计）。

---

## 修复（1 行 + 注释）

`main/protocols/websocket_protocol.cc::OpenAudioChannel()`，
在 `on_audio_channel_opened_()` **之前**补：

```cpp
if (on_connected_ != nullptr) {
    on_connected_();
}
```

**为什么放这个位置**：
- 正好是 WS 链路上"连接已建立 + 服务端 hello 已收到"的确定时刻
- 与 MQTT 版触发 `on_connected_` 的语义**等价**
- **不改变任何状态机逻辑**，只补上游漏掉的通知
- 两处失败路径（`SetError(SERVER_NOT_CONNECTED)` / `SetError(SERVER_TIMEOUT)`）
  都在 return 处提前退出，**不会走到这里** → 不会误报"已连接"

## ⚠️ 中途踩的坑：别自创协议

我一度想在 `OnDisconnected` 里造一个 `{"type":"clear_chat_message"}` 去清屏残留文案。
写完才想起来查 `application.cc:455+` —— 它只认这几种 type：

| type | 处理 |
|---|---|
| `tts` | start/stop/sentence_start |
| `stt` | ✅ |
| `llm` | ✅ |
| `mcp` | ✅ |
| `system` | reboot / sound / standby |
| `alert` | ✅ |
| 其他 | `Missing message type` 日志 + 静默丢弃 |

自造的 type **根本没人处理**，纯属白写。已撤掉。

而且断线清屏本来就被覆盖了：`on_audio_channel_closed_` →
`application.cc:445-451` 里已经做了
`display->SetChatMessage("system", "")` + `SetDeviceState(kIdle)`。

> **教训（与 `docs/34` 同款）**：服务端/固件之间的消息类型是**协议**，
> 照抄上游，别自创。看到"这里少个清屏动作"的第一反应应该是
> "**谁本来就负责清？**"，而不是"我造一个"。

---

## 新增判据：UI 状态 ≠ 连接状态

本次最大的教训：**服务端"设备上线"只证明 TCP/WS 通了，不证明 UI 状态被正确复位。**

排查这类"屏幕说失败、日志说成功"的矛盾时，**优先怀疑显示状态机**，
而不是继续挖网络。判断依据是"谁负责改这块 UI、它的触发条件满足了吗"，
而不是"网络通不通"。
