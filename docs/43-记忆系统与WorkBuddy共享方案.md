# 记忆系统：现状盘点 + 与 WorkBuddy 共享的方案（2026-10-03）

> 主人三个问题：
> 1. 性能要比网上自带版强
> 2. 本地知识库和记忆库是不是分开的？
> 3. 记忆能不能跟 WorkBuddy 共享，还是各存一份？目标是一个池子。

---

## 一、先说结论：知识库 ≠ 记忆库，Task 又 ≠ 记忆

我们这套系统里其实有**四类东西**，很容易混：

| # | 名称 | 存在哪 | 生命周期 | 谁写入 | 谁能查 |
|---|---|---|---|---|---|
| 1 | **对话记忆** | SQLite `memories` 表 | 永久（append-only） | LLM 调 `remember` 自动写 | `recall` 语义检索 |
| 2 | **待办（Task）** | SQLite `todos` 表 ★本轮新增 | pending→done/dropped | LLM 调 `add_todo` | `list_todos` / `todo_digest` |
| 3 | **知识库** | 外部（RAGFlow 服务） | 文档级 | 你手动上传 | `search_from_ragflow` 工具 |
| 4 | **WorkBuddy 记忆** | 工作区 `MEMORY.md` + 日志 | 长期 | 我（AI）维护 | 我读 |

**所以答案是：知识库和记忆库确实是分开的，是两个东西。**
- 知识库 = 你放的**外部资料**（像一本参考书），被动查、要有出处
- 记忆 = 小智**自己攒的**关于你的东西（像它脑子里的印象），主动攒、可模糊匹配

本轮补的第 2 类（Task）是**之前完全缺的**——这正是"主动关注我没做完的事"卡住的原因。

## 二、原来的记忆层：性能比官方强在哪

`bridge/memory.py`（2026-10-02 写的，不是开源项目自带的）：

| 维度 | 实现 | 强在哪 |
|---|---|---|
| 存储 | SQLite `bridge/memory/memory.db` | 零重依赖，不装 chromadb/faiss |
| 向量 | 本地 Ollama `nomic-embed-text` 768 维 | 数据不出网 |
| 关键词 | FTS5 trigram + 2-gram 重合 | **trigram 对中文友好**，纯关键词也不失准 |
| 混合打分 | `max(余弦相似度, 关键词分)` | 向量为主、关键词兜底 |
| 降级 | Ollama 挂了自动退纯关键词 | **绝不阻塞语音对话** |
| 分类 | chat / profile / project / knowledge / task | 比官方单一摘要强 |

**对比官方自带的 3 种**：
| 官方选项 | 问题 |
|---|---|
| `mem_local_short` | 纯摘要式，压缩后细节丢失 |
| `mem0ai` | 依赖外部 mem0ai 服务，数据出网 |
| `powermem` | 外部服务，同上 |

所以我们默认 `nomem`（关掉官方那套），自己用 `memory.py`——**性能和数据安全都更强**。

> 现状：库里有 6 条记忆（profile 3 / project 1 / knowledge 1 / chat 1）。

## 三、本轮新增：Task 层（打通"主动关注未完成的事"）

### 为什么单独建表，不塞进 memories

| | memories | todos |
|---|---|---|
| 语义 | 知识条目 | 待办事项 |
| 写入后 | 不管 | 会变（做完要标 done） |
| 需要字段 | 内容 + 标签 | 状态、截止时间、完成时间、提醒时间 |
| 查询 | 模糊语义匹配 | 精确状态筛选 |

塞一起会把语义搅乱，索引也没法用。

### 新增表结构

```sql
CREATE TABLE todos (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    title       TEXT NOT NULL,      -- 要做的事
    note        TEXT DEFAULT '',    -- 补充
    due         TEXT DEFAULT '',    -- 'YYYY-MM-DD' 或 'YYYY-MM-DD HH:MM'
    priority    INTEGER DEFAULT 2,
    status      TEXT DEFAULT 'pending',  -- pending / done / dropped
    created_at  TEXT NOT NULL,
    done_at     TEXT,
    reminded_at TEXT                -- 上次提醒时间，用来去重
);
CREATE INDEX idx_todos_status ON todos(status, due);
```

与 `memory.py` **共用同一个 SQLite 文件**，不新增文件。

### 中文时间解析（`normalize_due`）

主人说话不会说 ISO 格式，所以做了自然语言解析。**实测 18/18 通过**：

| 输入 | 结果 | 输入 | 结果 |
|---|---|---|---|
| 今天 / 明天 / 后天 / 大后天 | ✅ | 明早八点 | ✅ → 明天 08:00 |
| 三天后 / 两周后 | ✅ | 今晚八点 | ✅ → 今天 20:00 |
| 下周一 / 周三 | ✅ | 下午三点 | ✅ → 今天 15:00 |
| 10月5日 / 2026-10-05 08:30 | ✅ | 明天晚上 | ✅ → 明天 20:00 |
| 2月30日（非法） | ✅ → 空 | 随便什么时候 / 改天吧 | ✅ → 空（不当成今天） |

> 设计原则：**认不准就返回空**（当"没期限"），宁可漏报也不误报。

### 四个 LLM 工具

| 工具 | 什么时候会触发 |
|---|---|
| `add_todo(title, due, note)` | 主人说「提醒我…」「我得…」「别忘了…」 |
| `list_todos(status, limit)` | 「我还有什么没做」 |
| `done_todo(title)` | 「这件事做完了」（模糊匹配标题，只在明确说完成时调） |
| `todo_digest(include_all)` | 「我今天有什么安排」 |

### ★ 主动巡检（这才是重点）

`core/notify_plugin.py::_todo_watch_loop`：

```
每 10 分钟扫一次
  ├─ 早 07:00–09:00：做一次"今天要做 + 已过期"汇总（一天只做一次）
  │     "早上好。今天有开通火山语音合成；过期的有交房租。"
  └─ 全天：needs_remind() 挑最多 2 条到点提醒
        "提醒一下，开通火山语音合成，今天该做了。"
        念完打 reminded 戳，4 小时内不重复念
```

**降噪设计**（避免变吵闹）：
- 4 小时去重（`needs_remind` 内部）
- 一次最多念 2 条
- 早间汇总一天一次
- 设备离线时自动入队，联网后补播（复用现成的离线队列）

## 四、能不能跟 WorkBuddy 共享？—— 能，但要选对"共享面"

### 三种打通方式对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 文件互读**（推荐） | 小智读写工作区 `MEMORY.md`；待办导出 Markdown 给我 | 简单、可读、双向、我天然会维护 MEMORY.md | 需处理同步时机 |
| B. 共享 SQLite | 小智的库给我读 | 实时、无重复 | 我这边不认 SQLite，得转换 |
| C. 独立知识库服务 | 起个 memory 服务，两边都调 | 架构最干净 | 要多跑一个进程 |

### 推荐的共享结构

```
        ┌─────────────┐
        │  事实单一源   │  ← 谁都往这里写，只有一份
        └──────┬──────┘
               │
   ┌───────────┼───────────┐
   ↓           ↓           ↓
┌────────┐ ┌────────┐ ┌──────────────┐
│待办 todos│ │记忆 memories│ │MEMORY.md    │
│(SQLite) │ │(SQLite) │ │(工作区文件)  │
└────────┘ └────────┘ └──────────────┘
   小智语音    小智语音      我（AI）读写
```

**具体做法（下一步就做）**：
1. **我 → 小智**：我把项目状态写进工作区 `MEMORY.md`，小智的 `project` 类记忆指向它
2. **小智 → 我**：小智每次完成任务，除了 `bridge/done/` 播报，再往工作区写一行"今天小智记下了：xxx"
3. **待办共享**：小智的 `todos` 表定期导出成 `bridge/todo.md`（人可读），我在需要时读它

### 为什么不做 B/C
- **B**：我读 SQLite 得写转换代码，而 MEMORY.md 我本来就在维护，重复建设
- **C**：为一个桌面设备起常驻服务不划算，出问题时多一个故障点
