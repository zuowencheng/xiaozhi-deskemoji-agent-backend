## 一、提示音为什么没了：**我把格式换错了**（不是刷机失败）

`audio/audio_service.cc::PlaySound` 是**手写 Ogg 解析器**，它认的包头是：

```cpp
if (memcmp(pkt_ptr, "OpusHead", 8) == 0) { seen_head = true; ... }
if (memcmp(pkt_ptr, "OpusTags", 8) == 0) { seen_tags = true; }
```

**它只认 Opus in Ogg。** 而我昨晚换 200ms 提示音时用 soundfile 生成的是 **OGG Vorbis**：

```python
sf.write(path, y, sr, format='OGG')              # ❌ 默认 VORBIS
```

结果 `seen_head` 永远为 false → 所有 packet 被 `continue` 跳过 → **一个字节都不播，
而且日志里什么都不报**。所以你完全没听到，不是设备坏了。

### 正确写法（已改）

```python
sf.write(path, y, sr, format='OGG', subtype='OPUS')   # ✅ 必须 OPUS
# 校验：b.find(b'OpusHead') >= 0 and b.find(b'OpusTags') >= 0
```

两个文件都已重新生成为 Opus，校验通过：

| 文件 | 时长 | 内容 | 用途 |
|---|---|---|---|
| `popup.ogg` | 200ms | 880+1320Hz 双音 | 通用提示（备用） |
| **`listening.ogg`** | **150ms** | **1046Hz 单音，更轻** | **「可以说话了」** |
| `popup.ogg.bak-480ms` | 480ms | 原厂版 | 备份（你嫌它"呲"） |

## 二、「说完话就有提示音」——你要的正是这个

你的原话我记下了：

> 他说完话之后，立马有一个简单的提示音，我就知道我可以说话了。
> 不然我还得盯着小屏幕，等它切到"聆听中"我才会说话，很不顺畅。

**已实现**，而且时机是这么设计的：

```
小智说完 → 设备进 kDeviceStateListening → 播「叮咚」→ 你可以开口了
```

### 两个设计决定

**① 只在"进入聆听"时播，不在唤醒时播**

因为唤醒后**紧接着**就会进 listening，两个音连着响很怪。合成一个音，语义更清楚：
**"我听到了 + 你可以说"**。

**② 必须在开麦之前播**

```cpp
case kDeviceStateListening:
    audio_service_.PlaySound(Lang::Sounds::OGG_LISTENING);   // ← 这里，此时麦还关着
    if (!audio_service_.IsAudioProcessorRunning()) {
        protocol_->SendStartListening(listening_mode_);
        audio_service_.EnableVoiceProcessing(true);          // ← 开麦在后面
        ...
    }
```

这么排序的原因：**本板无 AEC**，如果开麦后播，提示音会被麦克风录进去、
可能被 ASR 当成你说的话。放在开麦前，提示音干干净净。

### 顺带记一笔

`main/CMakeLists.txt:601` 是 `file(GLOB .../assets/common/*.ogg)`，**GLOB 在配置时展开**，
所以新增 `listening.ogg` 后第一次编译直接链接失败（`ld returned 1 exit status`）。
修法（比重编译全量快得多）：

```python
删 build/CMakeCache.txt
删 build/esp-idf/main/CMakeFiles
```

固件已刷：**ELF `b98d8df81`**。

## 三、任务派发：**后台没偷懒，是"太认真"了**

我把网易云那个任务的完整时间线翻出来了：

| 时刻 | 事件 |
|---|---|
| 11:16:48 | 任务派发 `task-20261003-111648.md` |
| 11:16:49 | 执行器接手，开始干活 |
| **11:19:51** | **完成，耗时 182 秒 / 6 步** |
| 11:19:54 | 播报（`.mark` 已打，音频探针 55 包 / 8357 字节） |

执行结果原文：

> 我找遍了整台电脑，网易云音乐这个软件并没有安装，开始菜单和注册表里都没有它的踪影，
> 装的是酷狗音乐。要不要我帮您打开酷狗音乐？

**活儿干得相当漂亮**——查了开始菜单、注册表，如实汇报没装，还给了替代方案。
`done/` 里那个文件状态是 `done`，播报标记也打了。

### 那你为什么没听到

两个原因叠加：

1. **3 分钟完全静默**（11:16→11:19），设备一声不吭。你 11:16 派的活，11:19 才有动静，
   中间当然觉得"没处理"。
2. **文案太绕**。原来播报是 `"你让我办的事办好了。" + 原始结果`，
   前面一句废话，后面一大段，听不出结论。

### 两处已改进

**① 取件瞬间就回执**

```python
# notify_plugin._ack_task()
speak_or_queue(f"好的，正在处理：{title}", tag="task-ack")
```

现在流程变成：
```
你：「打开网易云音乐」
小智：「好的，正在处理：帮我打开网易云音乐这个软件…」   ← 立刻
      （后台干活中，你该干嘛干嘛）
小智：「帮我打开网易云音乐——主人，网易云没装，装的是酷狗…」  ← 3 分钟后
```

回执开关：`notify.task_ack_enabled`（默认开，不需要就关掉）。

**② 完成播报先给结论**

从 `"你让我办的事办好了。{result}"` 改成 `"{title}——{result}"`，
超过 110 字自动截断，控制在能一口气听完的长度。

### 关于"优先级"

执行器是 `max_parallel_tasks: 2` 的信号量，**没有排队问题**（同时最多 2 个任务并行）。
慢的原因纯粹是 AI 真的在一步步查——查注册表、翻开始菜单、找安装路径。
这个我不打算优化：**"认真"比"快"重要**，它宁可花 3 分钟也不瞎猜一个路径把电脑搞乱。
