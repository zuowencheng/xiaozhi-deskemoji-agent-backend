# 14 · deskemoji 加装摄像头 / 视觉跟踪舵机 —— 可行性评估

> 问题：deskemoji 能否加装摄像头，实现人脸/物体识别，跟踪人脸/人体/手，驱动舵机自动转动？
> 数据来源：2026-10-02 实测（板级源码 `board_config.h` / `emoji_board.cc`）+ 乐鑫官方技术博客与 ESP-WHO 文档。

---

## 一、结论先行

**能做，但"在 deskemoji 这块板子上加摄像头"这条路不划算，不建议走。**

拆成两句：

| 问题 | 答案 |
|---|---|
| ESP32-S3 能不能跑本地人脸检测？ | ✅ **能**，ESP-WHO + ESP-DL，S3 有 SIMD 加速，无需 NPU |
| deskemoji 能不能加摄像头实现上面的功能？ | ⚠️ **引脚上极限勉强、工程上不值得**，见第三节 |
| 有没有更好、更省事、效果更好的做法？ | ✅ **有**，把视觉放在 PC 上，deskemoji 只当"云台+表情"执行端（见第五节） |

---

## 二、能力边界（先把"能识别什么"划清楚）

以 **ESP32-S3** 本地推理为准，帧率取自公开实测数据：

| 能力 | S3 本地（ESP-WHO） | 实测帧率 | PC 端（OpenCV/MediaPipe） |
|---|---|---|---|
| 人脸检测（有没有脸、在哪） | ✅ 成熟 | QQVGA ~15fps<br>QVGA ~5fps | ✅ 几百 fps |
| 人脸识别（是谁） | ✅ 支持人脸库注册 | 同检测档位 | ✅ |
| 行人/人体检测 | ✅ 有 pedestrian 模型 | QVGA 2~5fps | ✅ |
| 手势识别（上下左右等固定手势） | ✅ 有 gesture 模型 | 中等 | ✅ |
| **手部关键点跟踪（21 点）** | ❌ **跑不动** | — | ✅ MediaPipe Hands |
| **通用物体识别（COCO 80 类）** | ⚠️ 有 YOLO11 模型，但很勉强 | HVGA ~2fps | ✅ |
| 实时视频流上传云端识别 | ❌ 小智固件不支持 | — | ✅ |

**三条要认清的边界：**

1. **ESP-WHO 的"手势识别"≠ 手部跟踪**。它识别的是"手向上/向下/画圈"这类**固定手势类别**，不是 MediaPipe 那种 21 个关键点的连续跟踪。要"手到哪跟到哪"，S3 做不到。
2. **帧率是硬约束**。人脸检测要在 QVGA 才勉强 5fps，压到 QQVGA（160×120）才 15fps。而"平滑跟踪"至少要 10fps 起。**160×120 的分辨率下，物体识别基本别想，人脸检测勉强能用**。
3. **小智固件里的摄像头 ≠ 实时视觉**。官方 `xiaozhi-esp32` 的 camera 功能是注册成 MCP 工具 `take_photo` —— **拍一张 → JPEG 编码 → base64 → 传给后台大模型 → 返回一段文字描述**。这是"问它这是什么"，不是"实时看着你"。

> ⚠️ **版本撞车（很容易被忽略的一条）**：ESP-WHO 当前要求 **ESP-IDF v5.5.x**；而官方小智 v2.5.0 主干要求 **v6.0.1+，推荐 v6.1**。**两者没法编进同一个工程**。也就是说"小智 + 本地视觉"这个组合，在版本层面就是对不上的——想合体得自己移植降级，成本不可控。

## 三、deskemoji 引脚冲突实测（这是"不值得"的核心理由）

从 `board_config.h` 读出的**真实占用**（不是猜的）：

| 功能 | 引脚 |
|---|---|
| OLED SSD1306（I2C） | SDA=**41** / SCL=**42** |
| 手势 PAJ7620U2（共用 I2C） | 41 / 42 |
| **舵机 MG90S 水平** | **11** |
| **舵机 MG90S 垂直** | **12** |
| 按键 BOOT / 音量+ / 音量− | **0** / **40** / **39** |
| INMP441 麦（SD/WS/SCK） | **6** / **4** / **5** |
| MAX98357 功放（DIN/BCLK/LRC） | **7** / **15** / **16** |
| 板载 RGB LED | **48** |

**已经吃掉 14 个 GPIO。再看 DVP 摄像头要什么：**

| DVP 信号 | 根数 | 冲突情况 |
|---|---|---|
| D0–D7（8 位数据） | 8 | ❌ 常用位 **11/12 被舵机占**、**16 被功放占** |
| XCLK / PCLK | 2 | ❌ **15 被功放占**、**7 被功放占** |
| VSYNC / HREF | 2 | ❌ **6 / 5 被麦克风占** |
| SIOD / SIOC（SCCB 控制） | 2 | ❌ **40 / 39 被按键占** |
| PWDN / RESET | 2（可省） | — |
| **合计** | **最少 14 根** | **全部挤在已被占用的引脚带上** |

**S3 剩余可用 IO 只剩约 14 个**（1,2,8,9,10,13,14,17,18,21,38,45,46,47），还要扣掉：

- **45 / 46 是 strapping 引脚**（VDD_SPI / boot 模式），拿来做高速数据线风险很高
- **19 / 20 是原生 USB**（你烧录就靠它）
- **33–37 大概率被 8MB Octal PSRAM 占用**

**结论：引脚数量上"刚好卡在生死线"，但组合上极其别扭**——不重打板几乎做不成，重打板就是推翻"赛博太白"这块成品。

**还有一层**：deskemoji 是**打样 PCB**，上面这些剩余 IO **有没有引到焊盘/排针上，是未知数**。如果没引出，就得上飞线焊到芯片脚上——那不是 DIY，那是维修。

## 四、第二个硬伤：云台行程被写死

`board_config.h` 里明确限了舵机行程（注释写的是"保护舵机"）：

```
SERVO_MIN_X / MAX_X = 90 ∓ 40   →  水平总行程 80°
SERVO_MIN_Y / MAX_Y = 90 ∓ 20   →  垂直总行程 40°
```

这是**给"表情动作"设计的行程，不是给"跟踪"设计的**。

- 跟踪要求：目标在画面里偏左，云台就左转，直到目标回中心
- 现实：目标一走出 80° 范围就**到限位了，只能眼看着目标跑掉**
- 想扩行程 → 得改限位 → 但限位是保护结构件的，改大了舵机会撞壳/堵转烧齿轮

> 💡 **正面看也不全是坏消息**：桌面场景下（人坐在桌前 0.5~1m），摄像头自身 FOV 约 60°，加上 80° 机械行程，能覆盖相当宽的范围。**"面对面的桌面陪伴"够用，"房间里跟着人走"不够用。**

## 五、三条路线对比（推荐 B）

### 路线 A：deskemoji 本地加摄像头 + ESP-WHO

| 项 | 情况 |
|---|---|
| 硬件改动 | ❌ 要重打板或飞线 14 根；摄像头必须**装在云台上**才能"跟" |
| 软件改动 | ❌ 小智主干 v6.1 vs ESP-WHO v5.5，版本冲突；要把 ESP-WHO 的 pipeline 塞进小智 board 类 |
| 帧率 | ⚠️ QQVGA 才 15fps，QVGA 掉到 5fps |
| 手部跟踪 | ❌ 做不到 |
| 评价 | **投入最大、效果最差，不建议** |

### ⭐ 路线 B（推荐）：PC 摄像头处理 → 网络发角度 → deskemoji 转云台

```
PC 摄像头（你本来就有）
   ↓  OpenCV / MediaPipe（人脸 / 手 21 点 / 全身姿态，随便挑）
   ↓  算出目标中心 vs 画面中心的偏移 → 目标 pan/tilt 角度
   ↓  通过已有的桥（HTTP / MCP）发一条指令
deskemoji：servo_controller 设置角度 → 云台转动
   ↓  循环（20fps 级别）
```

**为什么这条最强：**

| 优势 | 说明 |
|---|---|
| **零硬件改动** | deskemoji 一个螺丝都不用拧，云台和表情都是现成的 |
| **算力无上限** | PC 上 MediaPipe 手部 21 点、YOLO 物体识别、姿态识别全都能跑 |
| **软件改动极小** | `servo_controller.cc` **已经存在**，只需在小智 `mcp_server` 里注册一个"设置云台角度"的工具（如 `set_gimbal(x, y)`），PC 端调一下就行 |
| **复用已有架构** | 你的"电脑 = 唯一大脑"架构本来就长这样，这是**顺水推舟** |
| **可换摄像头** | 想升级直接换 PC 摄像头，不用碰板子 |

**代价（要认）：** 延迟比本地高（网络+检测，约 50~150ms）；PC 必须开机；摄像头得朝着桌面（桌面 USB 摄像头就行）。

### 路线 C：独立的"眼睛"板

买一块官方已适配的 S3-EYE 类板子（自带 OV2640 + 屏），自己跑 ESP-WHO，跟 deskemoji 各干各的（可串口/网络互通）。

- 优点：纯嵌入式方案，不依赖 PC，能当独立作品/毕设
- 缺点：花钱；两块板要同步；还是躲不开 15fps 和"手部跟踪做不到"

## 六、如果真要做，这四个坑躲不开（无论走哪条路线）

1. **舵机绝对不要从开发板 5V 取电。**
   MG90S 堵转电流能到 1A 以上，一转头板子就掉压重启（看起来像"固件死机"，其实是欠压）。**必须独立 5V 供电 + 与主控共地**（共地不共电源）。这条是新手最容易栽的坑。

2. **死区（dead zone）+ 低通滤波，一个都不能少。**
   检测框的坐标天然会抖，直接拿它算角度 → 舵机会像抽风一样左右猛抖。必须：① 目标偏离中心小于阈值就不动；② 角度输出做低通滤波。

3. **反馈震荡：摄像头在云台上，会"追自己的尾巴"。**
   云台一转 → 画面变 → 检测结果变 → 云台又转。阻尼不够就自己原地抖。
   → 加**速度限制（梯形速度曲线）**，别让目标角度一步跳到位。

4. **电源噪声会钻进麦克风。**
   舵机 PWM 噪声顺着电源/地线跑到 INMP441，语音识别质量直接掉档。**麦克风地线、摄像头排线要远离电机线**，5V 轨上并一颗大电容（≥470µF）。

## 七、一个意外的好消息：人脸识别 + 表情系统 = 很出彩

如果哪天真上本地视觉（路线 C），**ESP-WHO 的人脸识别（注册人脸库、认出具体是谁）在 S3 上是真能跑的**。而这台机器的核心卖点就是**表情动画 + 云台动作**。

组合起来的玩法：

- 识别到"主人" → 触发开心/打招呼表情 + 云台朝向说话人
- 识别到"陌生人" → 警惕表情 / 抬手势
- 没检测到人 → 待机打瞌睡动画

**这比"跟踪"更贴合这台机器的定位**——跟踪是"监控"的思路，识别+表情是"陪伴"的思路。这也是我如果自己做，会优先选的方向。
