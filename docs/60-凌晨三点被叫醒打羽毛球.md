# 60 · 凌晨 3 点被叫醒打羽毛球（待办巡检缺少可播时段）

> 时间：2026-10-04 03:01 — 03:25
> 现象：主人凌晨被设备叫醒，小智说「嗨，提醒一下，下午去打羽毛球，今天 15:00 该做了」
> 结论：**不是定时提醒的锅，是待办巡检**；根因是「12 小时预告窗口」没有时段下限。

---

## 一、事故现场（服务端日志铁证）

```
2026-10-04 03:01:19 core.notify_plugin  [播报] 已投递 ... sid=d136af1e:
                   嗨，提醒一下，下午去打羽毛球，今天 15:00该做了
2026-10-04 03:01:20 core.handle.sendAudioHandle  发送第一段语音: 嗨，提醒一下，下午去打羽毛球
2026-10-04 03:01:21 core.notify_plugin  [音频探针] 本次播报合计 86 个包 / 13330 字节
```

播报**真实发生**（86 个音频包、13KB），不是误听。

主人随后质问，模型的回答是错的——它去翻了定时提醒列表，说「定的是今晚 22 点」，
还说「是不是你记岔了」。**它查错了地方**，真正的播报源是待办巡检，不是提醒调度器。

---

## 二、根因：三个条件同时成立才出事

### 条件 1：播报源是「待办巡检」，不是「定时提醒」

两者前缀不同，一眼可分：

| 播报源 | 文案模板 | 代码位置 |
|---|---|---|
| 定时提醒 `_reminder_loop` | `提醒你：{text}` | `notify_plugin.py:1198` |
| **待办巡检 `_todo_watch_loop`** | **`提醒一下，{title}，{_human_due}该做了`** | `notify_plugin.py:859` |

日志里的前缀是「提醒一下」→ **待办巡检**。
（前面的「嗨，」是 `speak_or_queue` 的统一前缀，两类播报都有。）

再看数据源也对上了——`data/reminders.json` 里**根本没有**「下午去打羽毛球」这条，
而待办库 `bridge/memory/memory.db` 里有：

```
id=3  下午去打羽毛球   due=2026-10-04 15:00   reminded_at=2026-10-04T03:01:19
```

`reminded_at` 正是事故时刻——**戳是它自己打的，这就是凶器上的指纹**。

### 条件 2：`needs_remind(12)` 的预告窗口在凌晨就打开了

`bridge/todo.py:313`：

```python
def needs_remind(within_hours: int = 12) -> list[dict]:
    soon = (now + timedelta(hours=within_hours)).strftime("%Y-%m-%d %H:%M")
    ...
    if due <= soon:          # 12 小时内到期 → 该提醒
        out.append(t)
```

- 02:51 时 `now+12h = 10-04 14:51` < due `15:00` → **不命中**
- **03:00 整** `now+12h = 10-04 15:00` = due → **窗口打开**
- 巡检每 10 分钟扫一次 → 首次扫描落在 **03:01:19**

这解释了"为什么偏偏是 3 点"——不是随机，是数学必然。

### 条件 3：免打扰默认关，兜不住

上一轮做的 `quiet_hours_enabled` 按主人要求**默认 false**，
23:00–07:00 的静默窗口虽然覆盖了 03:01，但开关没开 → 等于没有。

> 教训：**默认关的安全网不能算安全网**。
> 对于"半夜把人叫醒"这种明确的负向行为，应该有一道**默认开**的闸。

## 三、修复：给待办巡检单独加一道「可播时段」（默认开）

### 改动清单

| 文件 | 改动 |
|---|---|
| `core/notify_plugin.py` | 新增 `_in_todo_speak_window()`（默认 07:00–22:00）；`_todo_watch_loop` 到点提醒前先过闸 |
| `data/.config.yaml` | `notify` 段加 `todo_speak_start: "07:00"` / `todo_speak_end: "22:00"` |
| `server/admin/admin_server.py` | EDITABLE 加 2 项（`time` 类型，17→**23** 项） |
| `docs/20`、`docs/42` | 可调项数量 17→23，并补上 6 项项名 |

### 为什么不做成「改小 within_hours」

直觉做法是 12 小时改小（比如 2 小时）。**但这治标不治本**：
- 改成 2 小时 → 13:00 才提醒，对"出门打球"太晚（要提前收拾）
- 改成 6 小时 → 09:00 提醒，但主人若睡到中午，09:00 照样是骚扰

真正错的是"**任何时刻都能播**"这个前提。时段闸是唯一正解。

### 两个关键设计决定

**① 与免打扰不合并，是两个独立开关**

| | 免打扰 `quiet_hours_*` | 待办时段 `todo_speak_*` |
|---|---|---|
| 默认 | **关**（主人自己决定） | **开** |
| 范围 | 所有主动播报 | 只管待办巡检 |
| 静默时 | 入队，出窗口补播 | 跳过（见下） |

关系是「或」：任一判定静默就不播。

**② 窗口外不打 `reminded_at` 戳** ⭐ 最重要的一条

打戳 = 系统认为"这条已经提醒过了"，接下来 4 小时不再念。
如果凌晨既播了又打戳，那白天真正该提醒的时间反而**永远不播**——
等于把消息弄丢了。所以窗口外直接 `need = []`，什么都不做。

---

### 现场验证（不只是单元测试）

重启后 03:24:29 巡检启动，立刻打出了留痕日志——**证明它是主动跳过，不是没跑**：

```
2026-10-04 03:24:29  待办巡检已启动（每 10 分钟扫一次）
2026-10-04 03:24:29  待办巡检：03:24 不在可播时段（07:00-22:00），跳过；不打已读戳，白天照常念
```

且此时待办处于「无闸必然命中」状态（`reminded_at` 已清空、due=今天15:00），
到 03:39 复查：**播报 0 次，`reminded_at` 仍为 NULL** → 闸拦住了，消息也没丢。

> 这条留痕日志是排查时补加的。原来的巡检在跳过分支**什么都不打**，
> 于是"该播的没播"和"巡检根本没跑"在日志上**长得一模一样**——事后无法区分。

## 五、我自己的两个失误（记下来防再犯）

### 失误 1：清戳触发二次播报

为了"让白天能正常再提醒一次"，我把 `reminded_at` 清成了 NULL。
但**当时旧进程还在跑**，4 小时去重失效 → 03:11:22 **又播了一遍**。

> 教训：**改数据库状态前先看有没有活进程正在读它**。
> 正确顺序是：先停服务 / 先部署新代码 → 再改数据。我反了。

### 失误 2：模型答错了却没人发现

主人问"为什么凌晨提醒"，模型去翻提醒列表、翻对话历史，
结论是"我没主动提过羽毛球""是你记岔了"。

**它没有能力查后台日志**，只能自圆其说。这类"模型对用户质疑编造解释"
的风险很高——以后凡是"为什么"类问题，应该由**有能力读日志的一侧**（助理）回答，
而不是让设备侧模型猜。
