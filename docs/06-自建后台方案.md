## 一、为什么要自建（先立靶子）

阶段一跑通的是：`设备 → xiaozhi.me 云 → MCP → 本机桥 → WorkBuddy`。
它有三个绕不过去的问题：

| 问题 | 后果 |
|---|---|
| 语音音频必须过公网 | 家里说什么，云端就听到什么 |
| MCP 是请求-响应式 | 设备不开口，云端不会来敲门 → **做不到真正的主动播报** |
| 能力受限于官方后台 | 记忆、任务编排、多设备都在别人手里 |

自建后台解决的是第 1、3 条，并为第 2 条提供实现的地基。

---

## 二、选型结论

**采用 `xinnan-tech/xiaozhi-esp32-server`（Python 版）作为底座**，不做 fork，改为「镜像源码 + 私有配置覆盖」。

理由（实测，不是听说）：

- 生态最大、更新最勤（10.7k star，主干仍在活跃提交）
- **官方文档化的私有配置机制**：项目根 `data/.config.yaml` 覆盖 `config.yaml`，密钥天然与源码分离 → 我们的仓库可以干净地保留全部源码而不泄密
- 我原先判断「Python 版没有主动下发、要从 Go 版移植」——**这个判断是错的，见下一节**

已排除的选项：

- **Docker 路线**：本机实测 `docker` 不存在、无 Docker Desktop、无 conda/uv/git，`HypervisorPresent=False`（虚拟化多半没开）。装 Docker 要动 BIOS + 装 WSL2，成本高且需要重启。**放弃 Docker，走免安装 Python 直跑**。
- **Go 版（hackers365）**：原本打算扒它的主动音频下发，现在不需要了。
- **Java 智控台（manager-api）+ Vue 管理台**：治理平台，阶段二用不上，暂不部署。

## 三、重要纠正：主动下发能力本来就有

翻源码翻出来的三处硬证据（都在 `server/xiaozhi-server/`）：

```
core/providers/tools/device_mcp/mcp_handler.py:103
    async def send_mcp_message(conn, payload)   # 服务端 → 设备 主动发 MCP 消息
core/providers/tools/device_mcp/mcp_handler.py:296
    async def call_mcp_tool(...)                # 服务端 主动调用设备端工具
core/connection.py:1413
    self.tts.tts_one_sentence(self, ContentType.TEXT, content_detail=text)
                                                # 服务端 主动合成并推送一句话
```

配套的 `listenMessageHandler.py` 里还有 `[device_call]` 指令通道——设备端能主动"来电"，服务端直接 TTS 播报而不经过 LLM。

**结论**：设备与服务端之间是一条长连接，服务端随时可以往设备推音频。我们要的「任务干完了小智主动开口」，不需要移植 Go 版代码，只需要在服务端加一个**外部触发入口**（HTTP 或小工具），让 WorkBuddy 完成后调用它。这是阶段二真正的自研增量，量很小。

## 六、各模块选型与隐私边界

| 模块 | 默认选型 | 数据出网？ |
|---|---|---|
| VAD | SileroVAD（本地 onnx） | ❌ 不出网 |
| LLM | **OllamaLLM / qwen3:4b（本机）** | ❌ 不出网 |
| TTS | EdgeTTS（微软在线，免费无 Key） | ⚠️ 合成文本出网 |
| ASR | 待定，**这是唯一必须做抉择的一环** | 见下 |
| Memory | nomem（记忆由我们自己的 `bridge/memory.py` 承担） | ❌ 不出网 |

**ASR 的两条路**：

1. **云端**（DoubaoASR / 腾讯 / 阿里）：需申请 Key，识别准确，但**你的语音会出网**。腾讯和火山都有免费额度。
2. **本地**（SherpaASR + SenseVoice 模型）：**完全离线**，模型约 230MB（后台已在下载）。代价是首次识别慢一点、占内存。

鉴于成哥把隐私列为 P0，**推荐本地 SherpaASR**；云端 Key 作为备选填着，随时可切（改 `selected_module.ASR` 一行即可）。

## 八、设备端接入：这一步躲不掉

**设备现在烧的固件里写死了 xiaozhi.me 的地址，不重编固件，它永远不会来找你本机的服务。**

可选路径（按推荐度排序）：

1. **本地重编固件（正路）**
   - 用社区板级代码 `esp32-s3n16r8-emoji`（来自 `TranBinh2311` 仓库）配上游 `78/xiaozhi-esp32`
   - 改 `CONFIG_WEBSOCKET_URL`（或 OTA 地址）→ 编出 `xiaozhi.bin`
   - 刷进 **ota_1 分区**（现在是空的），跟正在跑的 ota_0 并存，翻车切回去就行
   - 前提：装 ESP-IDF（几 GB，需要成哥双击 installer）
2. **配网页面改地址（待验证）**
   部分固件在 AP 配网页面里允许填自定义后端。需要在你家路由器里把设备踢进配网模式试一次，**成功率不确定**。
3. **自建后台当 MCP 后端、语音仍走云端（折中）**
   暂不改固件，只把 `mcp_endpoint` 指向自建服务；**不解决出网问题**，只解决能力扩展。

**我的建议**：走第 1 条，且**跟固件升级合并成一次做**——反正都要编译，一次编译同时解决「升级到新版本 + 指向自建后台」两件事，避免刷两次机冒两次风险。

## 九、自研增量：主动播报接口（设计）

目标：WorkBuddy 干完活 → 服务端让设备立刻开口。

设计（不改上游核心，只加插件 + HTTP 路由，方便后续跟随上游升级）：

```
POST http://127.0.0.1:8003/notify
{ "device_id": "84:c7:bb:58:17:44", "text": "你让我总结的项目进展，已经写好了" }

→ 服务端从连接表中找到该设备的 ConnectionHandler
→ conn.tts.tts_one_sentence(conn, ContentType.TEXT, content_detail=text)
→ 设备直接播报（设备处于 listen 态时无需唤醒）
```

需要解决的两个细节：

- 连接表：上游 `WebSocketServer` 目前不持有全局 conn 注册表 → 加一个 `dict[device_id] = handler`
- 打断策略：设备正在说话时来了新播报，是排队还是打断 → 默认排队，可配

## 十、风险与回滚

| 风险 | 应对 |
|---|---|
| 依赖装不完 / opus 编解码缺 DLL | 已最小化依赖；若 `opuslib_next` 报缺 DLL，换 `opuslib` + 手动放 DLL |
| 服务起不来 | 不影响阶段一：云端链路照常可用，两套并存 |
| 设备连不上自建服务 | 固件地址没改对 → 串口日志看 `Connecting to ws://...` |
| 刷固件变砖 | 已有回滚包（ota_0_app.bin / 全片 16MB），BOOT 键进下载模式可救 |
| 密钥泄密 | `data/` 与 `.env` 均已 gitignore；**聊天里贴过的 MCP token 和 GitHub PAT 建议重新生成** |
