## 一、一句话架构

> **小智 = 耳朵 + 嘴；自建后台 = 神经中枢；WorkBuddy = 手；投递箱 = 神经；播报通道 = 反馈。**

```
你说话
  ↓
deskemoji（ESP32-S3）  ── 唤醒词本地识别，音频链路走局域网
  ↓ ws://192.168.3.139:8000/xiaozhi/v1/
自建后台 xiaozhi-server（本机）
  ├─ VAD   SileroVAD    （本地 onnx，不出网）
  ├─ ASR   SherpaASR    （本地 SenseVoice，不出网）
  ├─ LLM   ★ DeepSeek API（待换，唯一出网的就是"文字"）
  └─ TTS   EdgeTTS      （微软在线，免费无 Key）
  ↓ LLM 判断意图
     ├─ 闲聊/查资料 ──→ 直接答（DeepSeek 自带联网能力）
     └─ 要干活 ──→ 调自研工具 pc_run_task
                      ↓ HTTP 127.0.0.1:8005
                   本机桥 bridge/（常驻，你双击启动）
                      ↓ 写文件投递箱
                   inbox/task-<id>.md
                      ↓ 取件（谁取，见 §六）
                   WorkBuddy（我）执行
                      ↓ 写回
                   done/task-<id>.md（口语化 ≤300 字）
                      ↓
                   POST 127.0.0.1:8004/notify
                      ↓
                   小智主动开口："你让我办的那事，办完了"
```

**关键设计原则**：LLM 调 `pc_run_task` **立刻返回"收到，我去办"**，不阻塞等结果。
任务在后台异步跑，跑完走播报通道回来。这样小智永远不会"卡住不说话"。

## 三、DeepSeek 怎么换（具体改法）

好消息：服务端的 `openai` provider **原生支持 function calling**（`response_with_functions` + `tools`），
而且代码里**已经把 `deepseek.com` 写进了"自动禁用思考模式"白名单**：

```python
# core/providers/llm/openai/openai.py:15
"deepseek.com": {"thinking": {"type": "disabled"}},
```

也就是说——**语音场景最怕的"思考模型磨蹭半天"这个坑，上游已经帮我们填好了**。

改法（`server/xiaozhi-server/data/.config.yaml`）：

```yaml
selected_module:
  LLM: DeepSeekLLM          # 原来是 OllamaLLM

LLM:
  DeepSeekLLM:
    type: openai
    model_name: deepseek-chat     # 要推理换 deepseek-reasoner，但语音场景别换
    base_url: https://api.deepseek.com/v1
    api_key: sk-你的key
```

要你提供：**DeepSeek API Key**。填完我一条命令重启验证。

## 四、延迟预算（为什么"实时交互"这次能成立）

上一轮卡住的根因不是架构，是**本机没有独立显卡**——qwen3:4b 有 86% 压在 i5-1135G7 的 CPU 上，
冷启动 17 秒出第一个字、之后 5 字/秒。换成云端 API 后：

| 环节 | 本地 Ollama（旧） | DeepSeek API（新） |
|---|---|---|
| ASR | 本地，约 1s | 本地，约 1s（不变） |
| LLM 首字 | **17s（冷）/ 0.55s（热）** | **约 0.5–1.5s** |
| LLM 吐字 | 5 字/秒 | 差不多 20–40 字/秒 |
| TTS | EdgeTTS 约 0.5s | 不变 |
| **体感总延迟** | **20s+（且排队会死锁）** | **约 2–3s** ✅ |

> 补充：本地模型那次还出现"HTTP 响应头都等不到"的死锁——因为一条卡住的请求会把整个队列堵死。
> 这条线**正式关闭**，不再投入。

## 五、⚠️ 主动播报的前提：设备必须"常连"（**最关键的一个决策**）

这是整个方案里唯一还悬着的技术约束。

**现状**：设备只在**唤醒词 / 按键**时才连 WebSocket，静默一段时间就断开。
服务端有个旋钮：

```yaml
# server/xiaozhi-server/config.yaml:61
close_connection_no_voice_time: 120      # 静默 120 秒 → 断开
```

**后果**：如果一个任务跑了 3 分钟，等你回来时设备早断线了 → `POST /notify` 返回 **503**，
"任务完成主动提醒"就变成"等你下次开口时顺带提一句"。

**源码核查结论（我查过了）**：

- 设备侧 `application.cc` 里**没有独立的空闲关闭计时器**（只有一个每秒刷新的时钟定时器）
- 断开由**服务端**的"无语音超时"驱动 → **改配置就能解决，不用重编固件** ✅

**三个选项，请你选**：

| 方案 | 做法 | 代价 | 推荐度 |
|---|---|---|---|
| **A. 调大超时** | `close_connection_no_voice_time: 120` → `86400` | 设备长期占一个 WS 会话；桌面插电设备无所谓耗电 | ⭐⭐⭐ **推荐** |
| B. 固件改常连 | 重编固件 | 要重新刷机，风险大，收益与 A 相同 | ⭐ |
| C. 不改，用"顺风车播报" | 任务结果挂在下一次对话的返回里 | **做不到真正的主动提醒**，与你的目标矛盾 | ❌ |

> 注：A 方案要配合验证——设备端在 VAD 静音后是否有"自动停止监听"的行为（`kListeningModeAutoStop`）。
> 若仍有自动断开，我在服务端侧把这条路径一并处理，**仍然不用碰固件**。

## 七、隐私边界（换 DeepSeek 之后变了什么）

你原本把隐私列为 P0，换成云端 LLM 后边界要重新画清楚：

| 环节 | 数据 | 出网？ |
|---|---|---|
| 唤醒词识别 | 音频 | ❌ **本地**，不出网 |
| VAD | 音频 | ❌ **本地** |
| ASR | 音频 | ❌ **本地**（SherpaASR） |
| **LLM** | **识别出的文字** | ✅ **出网（DeepSeek）** ← 唯一 |
| TTS | 合成文字 | ✅ 出网（EdgeTTS，微软） |
| 记忆 | 文本 | ❌ 本地 SQLite |

**一句话**：**你的声音不出网，出网的只有"文字"。** 这是本地 ASR + 云端 LLM 的折中，
比"全云端"好，比"全本地"快。如果你要连文字也不出网——那就得回到本地模型，而本地模型在你这台机器上跑不动，**这是个物理约束，不是技术选择**。

> 可选的第三条路：**混合路由**——敏感话题走本地（慢但不出网），日常闲聊走 DeepSeek。
> 需要你确认值不值得这个复杂度。

共享做成开关，避免调试期互相污染。

**你正在扫的历史磁盘 → 就是 `docs/13` 里那个"个人知识库"**：

1. **嵌入模型不一致，绝不跨库比向量**——知识库用 `nomic-embed-text`，本仓用 `bge-m3`，
