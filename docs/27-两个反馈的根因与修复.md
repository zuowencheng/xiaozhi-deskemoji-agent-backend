# 27 · 两个反馈的根因与修复（派活没执行 / 提醒不响）

> 时间：2026-10-02 21:20
> 用户反馈：①让查北京天气写 txt → 说"丢给助理了"但没执行 ②说 30 秒后提醒喝水 → 屏幕有倒计时但到点没响 ③（好消息）说话时表情会动了

## 一、结论速览

| # | 反馈 | 真根因 | 状态 |
|---|---|---|---|
| 1 | 派活没执行 | **执行者是「每小时一次」的定时任务**，任务单确实写进 inbox 了，只是没人干 | ✅ 已修：后台自己干，8.5 秒完成 |
| 2 | 提醒到点不响 | **双重根因**：<br>a) LLM 选了设备端自带倒计时，不是我们的 set_reminder<br>b) 设备 idle 不保持连接 + 固件硬编码 120 秒超时 → 播报没有通道可推 | ✅ 均已修（待刷机验证） |
| 3 | 表情不动 | 上一轮的修复生效 | ✅ 正常 |

**两条重要的认知纠错**（都是我之前判断错的，记下来别再犯）：

> ⚠️ **纠错一**：我原以为"改服务端 `close_connection_no_voice_time=86400` 就能让设备常连，不用改固件"。
> **错的。** 服务端参数确实生效了（实测合并后就是 86400），但**设备侧的断开不由服务端决定**。
>
> ⚠️ **纠错二**：设备不是"连了又断"，而是**"不唤醒就不连"**。复位后串口日志显示
> `STATE: idle` 之后再无任何 WebSocket 连接 —— 它压根没连过。

## 二、问题 1：任务派了却没人执行

### 证据
`bridge/inbox/` 里躺着任务单，格式完全正确：

```
- 任务编号：20261002-210724
- 来源：语音（小智 deskemoji）
- 状态：pending
## 任务内容
查询明天（2026年10月3日）北京的天气情况，把结果写成一个 txt 文本文件保存到桌面…
```

**说明 `pc_run_task` 完全正常**。缺的是"执行者"——原本由 WorkBuddy 的定时 automation 担任，
**周期是每小时一次**，所以体感就是"石沉大海"。

### 修复：新增 `core/pc_agent.py`（本机任务执行器）

让**自建后台自己把活干完**，不再依赖外部定时任务：

```
语音派活 → pc_control 写 inbox → 【新增】pc_agent 用 DeepSeek + 本机工具执行
        → 结果写进 done/ → watcher 主动播报
```

- **工具集（8 个）**：`run_shell` / `run_powershell` / `read_text_file` / `write_text_file` /
  `list_dir` / `open_path` / `web_fetch` / `list_processes`
- **路径智能**：`桌面/xx.txt` 自动解析成真实路径（兼容 OneDrive 重定向）
- **安全闸**：格式化、删系统目录、diskpart 等不可逆操作硬拦截
- **状态机**：pending → running（**先落盘**）→ done；进程崩了也不会重复执行
- **并发**：信号量限流（默认 2），由 `asyncio.to_thread` 调用，不阻塞事件循环

### 实测证据（真跑，非模拟）

```
[执行完成] 20261002-210724 ok=True 8485ms  → 北京明天10月3日多云，气温12到21度…文件已存到桌面
[执行完成] 20261002-210250 ok=True 32385ms → 酷狗音乐已经帮你打开了，现在正在运行中
```

桌面上真出现了 `北京明天天气.txt`（553 字节），内容是**从中国天气网抓的真实数据**：

```
北京明天天气（2026年10月3日）
天气：多云   气温：最高 21℃ / 最低 12℃   风力：3-4级
生活提示：穿衣较舒适…紫外线强…数据来源：中国天气网
```

**时延从「最长 1 小时」降到「几秒~几十秒」。**

## 三、问题 2：提醒到点不响（双重根因）

### 根因 a：LLM 选错了工具

服务端日志铁证：

```
21:08:19 执行工具: self_timer_create_countdown，参数: {'name': '喝水提醒', 'duration_ms': 30000}
21:08:19 客户端mcp工具调用 self.timer.create_countdown 成功
```

小智调的是**设备固件自带的倒计时**（所以屏幕会显示），而不是我们写的 `set_reminder`。
`data/reminders.json` 是 `[]` —— 我们的工具根本没被碰过。

**为什么提示词管不住？** `agent-base-prompt.txt` 里明明写了"提醒必须调 set_reminder"，
但设备端 MCP 提供了 **31 个工具**，`create_countdown` 字面上就是"倒计时"，
语义上比 set_reminder 更贴，模型选了更"直白"的那个。

**修复（代码层，不靠提示词）**：在 `ToolManager` 加**工具屏蔽表**：

```python
_EXCLUDED_TOOL_PREFIXES = ("self_timer_", "self_schedule_")
```

- `get_all_tools()` 里过滤 → LLM **根本看不到**这些工具
- `execute_tool()` 里二次拦截 → 万一模型幻觉调用，引导回 `set_reminder`
- 屏蔽理由：设备端倒计时/日程**只在本地显示，到点不会产生语音播报**，是"答应了做不到"的陷阱

> 经验：**功能重叠时，别用提示词去"劝"模型，直接从工具表里拿掉。**
> 也**不要**在提示词里写"不要用 XX"——负面提示反而会让模型想起 XX。

### 根因 b：设备 idle 不保持连接（这是更深的一层）

即使工具选对了，`set_reminder` 到点会用 `8004 /notify` 推语音 —— **但设备不在线就推不出去**。

**实测发现的真相（串口日志）**：

1. 复位设备 → `STATE: idle` → 之后 **200 秒内没有任何 WebSocket 连接**（不唤醒就不连）
2. 一次完整对话：`21:00:02 设备上线` → `21:10:16 客户端断开连接`（约 614 秒）
3. 服务端 `close_connection_no_voice_time` **实测合并后 = 86400**（24 小时）→ **不是服务端踢的**

**真凶在固件里**：

```cpp
// main/protocols/protocol.cc
bool Protocol::IsTimeout() const {
    const int kTimeoutSeconds = 120;   // ← 写死 120 秒
```

而 `WebsocketProtocol::IsAudioChannelOpened()` 里带着 `!IsTimeout()`：
**设备连续 120 秒没收到服务端数据，就自认为通道已废**。

**好消息**：播放链路本来就是通的，不用改：

```cpp
// application.cc —— 收到 tts start，idle 会自动切到 speaking 播放
if (device_state_ == kDeviceStateIdle || device_state_ == kDeviceStateListening) {
    SetDeviceState(kDeviceStateSpeaking);
```

**所以只差"保持连接"这一步。**

### 修复（固件，两处）

| 文件 | 改动 |
|---|---|
| `main/protocols/protocol.cc` | `kTimeoutSeconds` 120 → **3600**，空闲期不再误判超时 |
| `main/application.cc` | `MainEventLoop` 的每秒 tick 里加**保活**：每 5 秒检查，`idle` 且未连接就补上（对话中不打扰） |

保活逻辑：

```cpp
if (clock_ticks_ % 5 == 0 && device_state_ == kDeviceStateIdle
    && protocol_ && !protocol_->IsAudioChannelOpened()) {
    Schedule([this]() { ... protocol_->OpenAudioChannel(); ... });
}
```

## 四、附带的两个小修正

1. **loguru 占位符**：`pc_agent.py` 里误用了 `%s/%d`（loguru 只认 `{}`），日志打出来是
   `开始执行 %s：%s` 这种没被替换的原文。已批量改为 f-string（9 处，含 `unified_tool_manager.py`）。
2. **`list_processes` 判定不可靠**：pc_agent 看到 `KuGou.exe` 进程就认为"已打开"，
   但那可能是我早先 PoC 测试的残留进程。后续可改为"由本工具启动的才认"。
