# docs/33 · 主动播报「永远没声音」真因：AnimationTask 栈溢出

日期：2026-10-03 02:05
固件：ELF `7efc51ae1...`（刷 ota_1，ota_0 原厂保留）

---

## 结论先行

「主动播报没声音」**不是 TTS 没合成、不是连接断了**，而是：

> 设备收到播报 → 切 `speaking` → 触发 surprise 动画 → **AnimationTask 栈溢出 → 整机 Reboot**
> 音频还没出喇叭，芯片就已经重启了。

这一个 bug 同时制造了四个假象：

| 假象 | 真相 |
|---|---|
| 播报没声音 | 设备刚进 speaking 就死了 |
| 设备"频繁掉线重连" | 其实是**频繁重启**，每次都是新连接 |
| 串口日志"时间戳从头开始" | 抓到的正好是重启后 |
| 服务端日志一切正常 | 服务端确实发了，它不知道设备死了 |

---

## 决定性证据

`firmware/device_dump/serial_final.log`（2026-10-03 01:57:28 那次播报）：

```
21 I (224730) Application: STATE: speaking        ← 收到 tts/start，正常
27 I (224790) EmotionController: 触发情感: surprise
30 I (224800) EmojiController: 播放动画，类型: 4, 参数: 0
33 I (224820) EmojiController: 执行惊讶表情动画
34 ***ERROR*** A stack overflow in task AnimationTask has been detected.
35 Backtrace: 0x40381bd1:... |<-CORRUPTED
37 Rebooting...
40 rst:0xc (RTC_SW_CPU_RST),boot:0x8 (SPI_FAST_FLASH_BOOT)
```

复位原因 `0xc = RTC_SW_CPU_RST` —— **软件复位**，不是掉电、不是 WDT 超时、
不是 panic 断言。是 FreeRTOS 检测到栈溢出后自己调 `esp_restart()`。

---

## 根因

`emoji_controller.cc` 里 AnimationTask 创建时栈只给了 **4096 字节**：

```cpp
xTaskCreate(AnimationTask, "AnimationTask", 4096, this, 5, &animation_task_handle_);
```

而这条调用链 `AnimationTask → ExecuteSurprisedAnimation → LVGL 绘制 → 舵机`
实测需要 >4KB。平时随机动画（眨眼/左右看）勉强够用，所以看起来"一切正常"；
只有**主动播报触发 surprise 这条特定路径**会踩爆——因为它在 speaking 状态
切换的同一时刻被塞进来，栈上同时还压着状态机的上下文。

同一个文件里 `InitEmoji()` 有第二处 `xTaskCreate(... 4096 ...)`，
走那条路径时一样会溢出（已一并改）。

## 修复

### 1. 固件（已改 + 已编译 + 已刷 ota_1 + 已验机）

| 任务 | 原栈 | 新栈 |
|---|---|---|
| `AnimationTask`（`Initialize()` 内） | 4096 | **10240** |
| `AnimationTask`（`InitEmoji()` 内） | 4096 | **10240** |
| `AnimationTimerTask`（两处） | 4096 | **6144** |

验机：`ELF file SHA256: 7efc51ae1...` 与本地 `build/xiaozhi.elf` 一致。

### 2. 服务端（已改）

`core/notify_plugin.py`：

- **新增 `_conn_alive(conn)`**——投递前校验连接真的活着：
  - `conn.stop_event.is_set()` ⇒ 死
  - `ws.close_code is not None` ⇒ 死
  - `ws.state` 含 CLOSED/CLOSING ⇒ 死

  为什么必须加：`base.py` 的 `tts_text_priority_thread` 是
  `while not self.conn.stop_event.is_set()`，往一个 stop 已 set 的 conn 投消息
  **等于石沉大海，而且服务端日志完全正常**——这是最难查的一类失败。

- **设备上线自动补播**（`_flush_queue_on_online`）：断线期间攒下的话，
  上线 2.5s 后逐条补播（间隔 2s），播不出去的继续留在队列。

- **新增 `GET /notify/diag`**：打印每条连接的 `stop_event / ws_state /
  close_code / session_id`，并**发一帧裸 `tts/start` 探针**。
  判定方法：设备串口出现 `STATE: speaking` ⇒ 连接活，问题在 TTS 队列；
  毫无反应 ⇒ 连的是死连接。

## 排障方法论（这次踩出来的，值得记）

1. **别信"服务端发了"**。服务端日志干净 ≠ 设备收到。
   判定要靠**设备端串口有没有 `STATE: speaking`**。
2. **发一帧裸协议帧做探针**，能一秒区分"链路断"和"业务坏"。
3. **设备日志时间戳突然从 97 开始 = 重启**，马上去找 `rst:` 那一行，
   复位原因会直接告诉你方向：
   - `0xc RTC_SW_CPU_RST` → 软件复位（栈溢出 / esp_restart）
   - `0x15 USB_UART_CHIP_RESET` → 我手动 reset 的
   - `0x1 POWERON` / `0x10` → 掉电或看门狗
4. **`grep ERROR / stack overflow / Reboot`** 应该是看串口日志的第一步，
   我这次绕了一大圈才想到。

## 附带确认：语音打断在这块板上不可能实现

`serial_proof2.log`：

```
AFE: Input PCM Config: total 1 channels(1 microphone, 0 playback), sample rate:16000
AFE: AFE Pipeline: [input] -> |VAD(WebRTC)| -> [output]
```

**1 麦克风 + 0 回放通道** = AFE 拿不到喇叭的参考信号 = **做不了回声消除**。

配置层面也对不上：

- `CONFIG_USE_AUDIO_PROCESSOR=y`
- `CONFIG_USE_DEVICE_AEC`：sdkconfig 里**根本没这行**（默认 n），
  而且 Kconfig 里它的 `depends on` 只列了
  `ESP_BOX_3 / ESP_BOX / ESP_BOX_LITE / LICHUANG_DEV / KORVO2_V3 /
  Touch_AMOLED_1_75 / Touch_AMOLED_2_06 / P4_WIFI6_* / S3_LCD_EV_Board_2 / YUNLIAO_S3`
  —— **不含 `BOARD_TYPE_ESP32_S3N16R8_EMOJI`，想开也开不了**
- `CONFIG_USE_SERVER_AEC is not set`（且标注 Unstable）

所以 `aec_mode_ = kAecOff` → `SetListeningMode(kListeningModeAutoStop)`
→ 只有 `application.cc:674` 的 `AbortSpeaking(kAbortReasonWakeWordDetected)`
即**唤醒词打断**这一条路。

用户记忆中"用 xiaozhi.me 时能打断、很顺畅"的最合理解释：
官方服务端 TTS 出句快、句子短、间隙多，插话窗口大；
或实际插的是唤醒词。**不是语音打断。**（这块板换了官方服务端也一样）
