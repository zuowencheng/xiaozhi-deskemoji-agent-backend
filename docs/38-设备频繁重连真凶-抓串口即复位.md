# 「设备频繁重连」真凶：抓串口 = 给设备复位（2026-10-03 03:24）

## 一句话结论

**设备一直是稳定的。所谓"频繁断连"，是我自己抓串口造成的。**

串口日志里的铁证：

```
rst:0x15 (USB_UART_CHIP_RESET), boot:0x8 (SPI_FAST_FLASH_BOOT)
```

`rst:0x15` 的官方含义就是 **USB 串口把芯片复位了**，不是栈溢出、不是看门狗、不是掉电。

## 排查过程（别再走一遍）

### 现象
服务端日志里设备"上线"每 1~8 分钟一次（01:50~03:06 共 52 次），
但**"客户端断开连接"一次都没有**——真断线服务端一定会记断开，这个不对称就是破案点。

### 关键对照

| 设备启动 | 我的串口抓取 | 重启 | 间隔 |
|---|---|---|---|
| 02:56:15 | 02:57:05 结束 | 02:57:08 | 3 秒 |
| 02:57:08 | 02:59:xx 结束 | 02:59:27 | ~20 秒 |
| 02:59:27 | 03:06:49 结束 | 03:06:57 | 8 秒 |
| 02:59:27 | **不抓串口** | — | **连续跑 13.3 分钟零重启** |

三次都是"我一关串口它就重启"，静置时一次都不重启。

### 反证（我踩的坑）
我一度以为"控制线惹的祸"，在 `s.open()` 后面加了 `setDTR(False)/setRTS(False)` 想按住控制线。
结果**更糟**——再抓一次，日志第一条就是启动信息，说明 **open() 的瞬间就复位了**
（拉低 DTR 正好是 esptool 复位脉冲的前半段）。

已撤销，改回"什么都不做"。

## 现在的规矩

1. **`tools/read_serial.py` 里绝对不要碰 `setDTR` / `setRTS`**。
   当前行为：抓完日志 `close()` 时才复位一次，不影响采集。
2. **判断设备稳不稳，不许用"服务端上线次数"**——先问"刚才抓没抓串口"。
   正确方法：静置 10 分钟不动串口，再看 `grep "OTA请求设备ID" tmp/server.log` 有没有新增。
3. 看到 `rst:0x15 (USB_UART_CHIP_RESET)` 一律按"人为复位"处理，别当 bug 修。
   真崩溃长这样：`rst:0xc (RTC_SW_CPU_RST)` + `stack overflow` / `Guru Meditation`。
