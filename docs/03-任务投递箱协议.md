# 03 · 任务投递箱协议（小智 ↔ WorkBuddy 的契约）

> 这一份是本项目的**核心契约**。改目录结构或字段前先读它，桥（`bridge/server_agent.py`）和助理侧必须同时改，否则任务会石沉大海。

## 为什么用投递箱，而不是直接调引擎

实测（2026-10-02）：

| 方案 | 可行性 | 结论 |
|---|---|---|
| CLI 调用（`codebuddy -p` / `codex`） | ❌ 本机未安装任何 CLI | 走不通 |
| 读环境变量拿引擎凭据 | ❌ 进程环境里没有 `WORK*`/`CODEX*`/`MCP*` 相关变量 | 凭据是 App 注入的，外部进程拿不到 |
| 直连引擎 HTTP 端口 | ❌ 端口动态、且沙箱进程会被回收 | 不稳定 |
| **文件系统投递箱** | ✅ 落盘即契约，谁都能读写 | **采用** |

投递箱的好处是**解耦**：桥只管写，助理只管读，两边不需要知道对方怎么实现。哪怕助理换人（Codex / Claude / 别的），协议不变。

## 目录结构

```
bridge/
├── inbox/      待办。桥写入 task-<id>.md，status: pending
├── done/       已完成。助理执行完搬进来，并填「执行结果」
├── announced/  已播报标记（<id>.mark），防止小智重复念
└── outbox/     （旧版遗留，已弃用）
```

## 文件格式（`task-<id>.md`）

```markdown
# 任务 20261002-033310

- 任务编号：20261002-033310
- 创建时间：2026-10-02 03:33:10
- 来源：语音（小智 deskemoji）
- 状态：pending          ← 助理改成 done

## 任务内容

帮我用一句话总结今天小智 deskemoji 项目的进展

## 执行结果

（助理填写，纯文本，会被念出来，所以写口语化短句）
```

## 助理侧执行规范（WorkBuddy / automation 遵循）

1. 扫描 `inbox/task-*.md`，**没有就立刻结束**，不产出任何文字
2. 逐个读取 `## 任务内容`，用自身能力完成任务
3. 把结果写进 `## 执行结果`（**口语化、300 字内**，因为要念给主人听）
4. 把头部 `状态：pending` 改成 `状态：done`
5. 把整个文件**移动**到 `done/`（注意是移动，不是复制，否则会被重复执行）

## 回执机制：云方案下如何"主动告诉设备"

⚠️ **架构限制**：阶段一走 xiaozhi.me 云端托管，MCP 是**请求-响应式**——只有设备先开口，云端才会调我们的工具。云端不会主动往设备推音频（那需要自建服务端拿到设备通道，见阶段二）。

所以在阶段一用**"搭顺风车播报"**：

- 每个工具的返回值末尾都会挂一段 `_tail()`：检查 `done/` 里有没有**未播报**的完成结果，有就附带在返回文本里
- 效果：主人随便问一句（哪怕只是"电脑卡不卡"），小智都会顺带说"对了，你之前让我做的 XX 已经完成了……"
- 取走即写 `announced/<id>.mark`，**不会重复念**
- 也有独立工具 `get_pending_results`，主人直接问"刚才那事怎么样了"时用

阶段二自建后台后，换成 **Go 版主动音频下发**（`hackers365/xiaozhi-esp32-server-golang` 有现成实现），做到任务一完成设备立刻开口，不用等主人先说话。

## 实测记录（2026-10-02 03:33）

```
dispatch_agent("帮我用一句话总结今天小智项目的进展")
  → 任务已交给助理，编号 20261002-033310
inbox/task-20261002-033310.md 生成
助理执行 → done/task-20261002-033310.md（状态改 done）
get_pending_results() 第一次 → 念出结果 ✅
get_pending_results() 第二次 → "暂时没有新完成的任务" ✅（不重复）
```

## 定时执行（automation）

投递箱本身不干活，需要有人定期来取。已建定时 automation：每天 9:00–23:00 整点扫描一次 inbox。
不想要就暂停它——那时任务会一直躺在 inbox，需要主人在 WorkBuddy 里手动说一句"处理 inbox"。
