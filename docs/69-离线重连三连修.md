## 1. 问题一：MCP 重连后全部 Timeout（33 个工具全没）

### 现象

```
17:24:26 ERROR-Failed to initialize MCP server xiaozhi-local: Timeout
17:24:26 ERROR-Failed to initialize MCP server xiaozhi-pc: Timeout
17:24:26 ERROR-Failed to initialize MCP server xiaozhi-life: Timeout
17:24:37 ERROR-Failed to initialize MCP server xiaozhi-life: Timeout
17:24:37 ERROR-Failed to initialize MCP server xiaozhi-pc: Timeout
```

函数列表从 57 个掉到 32 个（只剩 local 的 8 个 + 设备/服务端工具）。

### 根因

`mcp_manager.py:57` 上游把初始化超时**写死 10 秒**：

```python
await asyncio.wait_for(client.initialize(...), timeout=10)
```

而我们的自研 MCP 冷启动很重：

| 模块 | 耗时 |
|---|---|
| `import local_mcp`（含 mcp 包 + pydantic） | **5.63s** |
| `import server_agent` | 1.57s |
| `import pc_agent` | 0.28s |

三个 MCP 并行启动（`asyncio.gather`），CPU/磁盘争抢下卡在 10 秒边界。
probe 实测：**串行合计 77 秒**。

### 修法

超时 10 → **45 秒**（一行，附注释说明为什么）。

```python
# 超时 10→45 秒（2026-10-13 改）。
# 上游写死 10 秒是给 npx 类云端 MCP 用的；我们的自研 MCP（local/pc/life）
# 要 import mcp 包 + pydantic（约 5.6s）+ server_agent（约 1.6s）...
await asyncio.wait_for(client.initialize(...), timeout=45)
```

### 验证

两次重启（17:44:31、17:48:58）三个 MCP 全部连接成功，无 Timeout。

## 2. 问题二：补播风暴，把 TTS 额度烧穿

### 现象

17:23:06 ~ 17:24:26 两分钟内，**每 2 秒一条**补播，共 59 条，内容高度重复：

- `tag=todo-due`："嗨，提醒一下，给手机换新膜，已经过期 N 天该做了"
- `tag=quota-low`："嗨，提醒一下，语音合成2.0的免费额度只剩1591字符了"

结果：**TTS 2.0 免费额度从满额烧到只剩 545/20000**。

### 根因（两层）

1. **入队无去重**：`enqueue()` 直接 `append`，没有任何判重。
2. **巡检持续生产**：待办巡检每 10 分钟判一次"需要提醒"，而窗口外
   **不打 `reminded_at` 戳**（打戳会导致白天该念的永远不念——这是之前
   docs/60 的设计），于是离线 5 天里每次巡检都重新入队一条。
   文本里"已经过期 N 天"的 N 还在涨 → **纯文本比对去不了重**。

### 修法

**a) 去重键 = `tag + 文本前 14 字`**

- 同一条待办：前缀"嗨，提醒一下，给手机换新膜"稳定，天数变化在后段 → **命中**
- 不同待办：前缀不同 → **不误伤**
- 命中则**整条替换**（保留最新状态，比如最新的剩余天数）

**b) 队列超 30 条丢最旧**（兜底，防去重失效时烧穿额度），并打 WARNING 留痕

**c) `_drain_queue` 每条之间加 6 秒间隔**——宁可慢点念完，别一上来机关枪

### 验证

新增 `tools/test_enqueue_dedup.py`，**9/9 通过**：

| 用例 | 结果 |
|---|---|
| 同待办天数变化只留 1 条（保留最新） | PASS |
| 两条不同待办都保留（不误伤） | PASS |
| 不同 tag 各留一条 | PASS |
| 空白文本不入队 | PASS |
| 超 30 条截断 + 丢最旧 + 最新还在 | PASS |
| 前缀一致时仍去重 | PASS |

## 3. 问题三：TTS 低水位不切换

### 现象

2.0 通道只剩 545 字符（2.7%），`pick_channel()` 仍然选它——再说 8 句就归零。
虽然归零后会自动切 1.0（兜底不哑），但用户会**在一句话说到一半时突然换音色**。

### 修法

`bridge/quota.py` 加低水位机制：

```python
_LOW_RATIO = 0.05   # 剩余低于 5% 就提前切

# remaining() 增补字段
"low": total > 0 and 0 < left <= total * _LOW_RATIO,

# pick_channel() 跳过 low
if not (info["exhausted"] or info["low"]):
    return ch
```

### 验证

```
豆包语音合成2.0: 剩 545 (2.7%)  exhausted=False low=True
语音合成1.0:     剩 20000 (100%)  exhausted=False low=False
pick_channel -> 1.0   ✅
```

**1.0 通道满额从没用过**，音色是 `zh_female_wanwanxiaohe_moon_bigtts`（湾湾小鹤），
和 2.0 的 uranus 不同。下次说话会自动切过去并打日志。
等 2.0 额度重置（火山按月）后，把账本 `used` 归零即可切回。

## 5. 遗留

- **TTS 音色**：现在会切到 1.0 的"湾湾小鹤"。若想保持 uranus，需要等 2.0 额度
  月度重置后手动把 `bridge/quota.json` 里 `2.0.used` 归零。
- **`quota-low` 提醒本身烧额度**：额度越低越该闭嘴，但现在的逻辑是"快没了"
  才提醒。可以考虑把告警阈值提高到 10%，且低水位后不再重复提醒
  （`mark_alerted` 已有时间戳去重，可复用）。
- **MCP 启动慢**（5.6s/个）没根治，只是把超时放开了。若以后 MCP 数量增加，
  考虑合并成单进程或给 mcp 包做预热常驻。
