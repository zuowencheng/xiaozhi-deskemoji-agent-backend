主人反馈三件事，第一件最关键：**后台显示播报成功，但设备就是不出声**。
本轮定位到根因并修复。

## 一、主动播报为什么一直没声音（根因）

### 排查路径

先确认"后台到底发没发"：

```
[播报] 已投递 FULL(FIRST/TEXT/LAST) sid=34f6342d
发送第一段语音: 测试播报通道…        ← 修复前**从来没有这一行**
发送音频消息: SentenceType.LAST
```

修复前日志只有 `主动播报已下发`，**没有 `发送第一段语音`**
= TTS 压根没合成出音频。设备端串口也印证了：收到文本后
只有 `EmotionController` 的动画分支，**全程无播放痕迹**，
且 `AudioCodec: Set output enable to false`（输出是关的）。

### 四个叠加原因（对照 `core/providers/tts/base.py`）

| # | 位置 | 问题 |
|---|---|---|
| 1 | `tts_one_sentence()` | 只把文本塞进 `tts_text_queue`，**从不发 `SentenceType.LAST`**。 |
|    | `_get_segment_text()` | 短句（"提醒你：喝水"）凑不够一个分段 → 返回空 → 文本一直憋在 `tts_text_buff`。只有 `LAST` 才会走 `_process_remaining_text_stream` 冲出来。**短句永远不成音。** |
| 2 | `tts_text_priority_thread:379` | `if message.sentence_id != self.conn.sentence_id: continue` —— ID 对不上直接丢弃 |
| 3 | `open_audio_channels()` | `tts_priority_thread` / `audio_play_priority_thread` 只在开音频通道时启动；设备 idle 久了线程已退出 → 队列无人消费 |
| 4 | `tts_text_priority_thread:375` | `if self.conn.client_abort: continue` —— 上次对话被打断过，后续播报全被跳过 |

### 修复（`core/notify_plugin.py::speak`）

不再调 `tts_one_sentence`，改为自己投**全套三件套**：

```python
target.client_abort = False                  # ④ 清打断标记
# ③ 线程不在就重新拉起
if 线程已死: tts.open_audio_channels(target)
sid = uuid4().hex
target.sentence_id = sid                     # ② 同步 sentence_id
q.put(TTSMessageDTO(sid, FIRST,  TEXT, ""))
q.put(TTSMessageDTO(sid, MIDDLE, TEXT, text))
q.put(TTSMessageDTO(sid, LAST,   TEXT, text))  # ① 冲出缓冲区
```

### 附带发现：文本会被表情指令吞掉

```
Application: << 听到请眨眨眼
EmotionController: 检测到眨眼命令     ← 含"眨眼"二字被当成动画指令
EmotionController: 识别为表情动作命令，处理完毕   ← 然后就没下文了
```

播报文本若含"眨眼/点头"等关键词，会被 `EmotionController` 拦截成动画命令，
**不送去 TTS**。规避：播报文案避开这些词（固件侧改需重刷，暂未动）。

## 二、删完文件没反馈 / 桌面不刷新

### 没反馈
与第一节同源——完成播报走的是同一条 `speak()`，修好即可。

### 桌面还显示旧文件
新增 `core/pc_desktop.py::refresh_desktop()`：枚举
`CabinetWClass` / `ExploreWClass`（资源管理器窗口），`PostMessage` 发 F5。
只刷文件窗口，不抢焦点、不影响别的程序。

并在 `pc_agent.execute_task_file()` 收尾**自动调一次**（任何文件操作后都刷），
不用每类操作各写一遍。实测：`已刷新 1 个资源管理器窗口`。

### 返回慢
取件 watcher 轮询 `5s → 2s`（完成播报更快）。
剩下的耗时在 LLM 多轮工具调用本身（DeepSeek，8–30s），属固有开销。

## 三、湾湾小何 V2：需要火山引擎密钥

**关键认知纠正**：小智生态里的"湾湾小何"**不是 Edge TTS 的音色**，
是**火山引擎（豆包）**的音色：

| 名称 | voice | 说明 |
|---|---|---|
| 湾湾小何 V1 | `zh_female_wanwanxiaohe_moon_bigtts` | 需在火山控制台开通 service/10007 |
| **小何 2.0** | `zh_female_xiaohe_uranus_bigtts` | 豆包语音合成 2.0，**"甜美活泼女声，有明显台湾口音"** ← 大概率就是主人要的 V2 |

Edge TTS 没有"湾湾小何"，只有 `zh-TW-HsiaoChenNeural`（台湾腔女声，当前在用）。

**要换 V2，需要提供火山引擎的 `appid` + `access_token`**
（当前 `data/.config.yaml` 里还是占位符 `你的火山appid`）。
另注意：豆包**大模型版本语音合成仅对企业实名认证用户开放**。

## 四、说话打断：现状与代价

固件 `application.cc::WakeWordInvoke`：

```cpp
} else if (device_state_ == kDeviceStateSpeaking) {
    AbortSpeaking(kAbortReasonNone);   // 只有唤醒词才打断
}
```

**现在能打断，但只能靠喊"你好小智"**，普通说话不行。

为什么业界普遍这么做：设备在自己放音时，麦克风听到的主要是喇叭回声，
没有硬件 AEC 参考信号就分不清"人声"和"自己的声音"，
贸然开全双工极易**自己把自己打断**（说两句就停、反复被打断）。

真要做"我开口它就停"，需要：AEC 参考信号 + speaking 态持续 VAD 检测
（建议 >500ms 连续人声才判定，并加能量阈值防误判）。
改动在固件侧，且设备当前有频繁掉线重连现象，刷机风险偏高。
